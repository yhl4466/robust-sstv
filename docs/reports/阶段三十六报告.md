## 1. 探针越界 bug 的修复（报告第 1 项）

### 1.1 修复内容（已实施）

```js
const nextPow2 = (v) => { let n = 256; while (n < v) n <<= 1; return n; };

function probeBand(x, at, len, lo, hi) {
  len = Math.max(8, Math.round(len));
  const n = nextPow2(len);           // 变换长度由窗长派生，永不小于窗长 ✓
  ...
  let used = 0;
  for (let i = 0; i < len; i++) { ...; used++; }
  if (!used) return { hz: NaN, ... };  // 显式处理，不再静默丢弃 ✓
```

**窗长与变换长度解耦** ✓ 且**变换长度由窗长派生**（`nextPow2(len)`）→ **结构上不可能再越界** ✓
`used` 计数并对 0 情形显式返回 NaN ✓（不再静默）

### 1.2 ⚠️ 我的纯音测试自身写错了单位

```
[任务 1] 合成纯音测试
  窗长       FFT   输入Hz   读出Hz    误差Hz
  0.25 ms     256     1900   2054.38   154.375
  0.25 ms     256     1200   2023.88   823.881
  0.004 ms    256     1200   3078.86  1878.859
```

**"0.25 ms" 实际是 12 个采样** ✗ —— 我在表里写 `lenMs = 0.25`，代码算 `len = 0.25/1000*48000 = 12` ✗
**我本意是 250 ms** ✓ 于是 `nextPow2(12) = 256`，**12 采样窗 + 256 点 FFT** →
频率分辨率名义 187.5 Hz 而**窗本身只有 12 采样（0.25 ms）** ✗ → 读数全无意义 ✓

**→ 任务 1 的失败有一半是我的测试写错** ✗ **但它也暴露了真问题**（见 §2）✓

## 2. 合成 S1 的校准结果（报告第 2 项）—— **探针算错了**

### 2.1 读数

```
合成音频 110.643 s · 解码器逐行参考 256 行
探针窗长 51.4 采样（= 像素 × 2.48，与生产 windowFactor 一致）

第 128 行：逐槽读出 vs 真值
 px   真值Hz   G读出   B读出   R读出
  0   1500.0    714.7    727.9    713.9

全行 320 像素 × 3 槽:
  G 槽 平均误差 952.1 Hz · B 槽 952.5 · R 槽 952.1
  最大误差 1530.8 Hz · 落在 1500–2300 内 0/960 (0.0%)
```

### 2.2 ★ 关键判读：**这是物理上不可能的值**

**合成 S1 的频谱里没有任何低于 1200 Hz 的能量** ✓
（同步音 1200、分隔音/台阶 1500、图像带 1500–2300；连标定头也是 1900 + 1100/1300）✓
**而探针读出 ~715–745 Hz** ✗✗ → **这个频率在信号里根本不存在** ✓

**且 730 ≈ 1500 × 0.487 ≈ 一半** ✓ 三槽的误差几乎相同（952.1 / 952.5 / 952.1）✗
→ **不是"某个槽位置错"，而是"探针的算法错"** ✓✓

**三个槽误差几乎相同**这一点尤其有价值 ✓：
若问题在槽位置，三槽误差应当不同 ✗ **它们一样，说明是共同的算法环节** ✓

### 2.3 已排除的环节

| 环节 | 是否可疑 | 依据 |
|---|---|---|
| 窗长 > FFT 长度（越界） | **已修** ✓ | `nextPow2(len)` 结构性保证 ✓ |
| 槽位置（`STARTS`） | **不太可疑** | 三槽误差相同（952.1/952.5/952.1）✗ 位置错不会这样 ✓ |
| 标定 | **已排除** | 合成 S1 上未应用任何标定 ✓ 仍错 ✓ |
| **FFT 调用 / bin↔频率换算** | **高度可疑** ✗ | 读数恰为真值的一半，且落在信号里不存在的频段 ✓ |

**"恰为一半"** 这类偏差在 FFT 用法里有两个经典来源 ✓：
- **`realTransform` 的输出布局与我的 bin 索引不一致**（例如我把它当复数交错数组用）
- **零填充后的 bin 间距**用错（用了窗长而非变换长度，或反之）

**本项目的生产代码用同一套 FFT 且工作正常** ✓（照片往返 30.50 dB）✓
→ **是我的调用方式与生产不同** ✗ **下一步应直接对照生产 `Estimator.peak` 的调用序列** ✓

## 3. `syncResidualRms` 偏大的根因（报告第 3 项）—— **已确定**

```
[任务 3] 解码器逐行参考自身的直线拟合
  斜率 20552.99 采样/行（标称 20554.56 ✓ 误差 -0.008%）· 残差 RMS 119.7 采样 · 最大 -476
  解码器自报 syncResidualRms = 20822.7 采样
  => 逐行参考本身【高度贴合直线】
```

### 3.1 结论

| 量 | 值 | 判读 |
|---|---|---|
| **逐行参考的直线拟合残差 RMS** | **119.7 采样**（0.25 行）✓ | **参考本身是干净的** ✓ |
| 该拟合的斜率 | **20552.99**（标称 20554.56）✓ | **误差仅 −0.008%** ✓✓ |
| **解码器自报 `syncResidualRms`** | **20822.7 采样** ✗ | 与上者相差 **174 倍** ✗ |

**→ 那个 20822 的残差【不可能】来自逐行参考** ✓
（若逐行参考的残差是 20822 采样 ≈ 一个行周期，那 256 行的参考就是**完全随机**的，
**拟合斜率不可能精确到 −0.008%** ✗✗）

**→ 它来自标定前导阶段（`calibration` 的 `obs`）那处独立拟合** ✓
**而那个拟合产出的 `scale = 1.0973 / offsetHz = −184.9` 被当作全图标定应用** ✗

### 3.2 与 `syncResidualRms` 的代码路径对照

从阶段二十二/二十九读过的代码：
- `calib.syncResidualRms = cal.residualRmsSamples`（来自标定前导 `obs` 的拟合）✓
- 该拟合的残差用 `bigThreshold = max(2, nominalLineSamples * 0.03)` = **616 采样** 判定"错锁行" ✓
- **残差 RMS 20822 远超 616** → **几乎所有行都会被标为错锁** ✓
  但 `cal.mislockedLines` 我没打印 ✗（下一轮补）

**→ 根因表述**：**标定前导阶段的同步检测在该录音上失败**（产出一个残差约等于行周期的"拟合"），
**而它的结果没有被质量门拒绝，直接被采用为全图标定** ✗✓

## 4. 两套标定的对比（报告第 4 项）

```

          → 1200 标称 对应原始 1131.82 Hz
```

| 项 | 同步拟合（**被采用**）✗ | HEADER 拟合 ✓ |
|---|---|---|
| 输入数据 | 前导阶段检出的同步位置 `obs` ✗ | 1900 Hz 前导音 + VIS 比特（1100/1300 Hz）✓ |
| **拟合质量** | **残差 RMS 20822 采样** ✗✗（≈ 一个行周期） | 自洽 ✓：`leaderFreqHz = 1899.91`（标称 1900，误差 **0.005%**）✓ |
| 隐含的 1200 Hz 原始频率 | 1131.82 Hz ✗ | **1207.05 Hz** ✓（与"无搬移"一致 ✓） |
| 是否被应用 | **是** ✗ | 仅用于 `afcMode:'affine'` 的一个分支 ✓ |
| 与"时间轴正常"是否相容 | 不相容 ✗（+9.7% 的尺度会让行周期也偏） | **相容** ✓ |

### 4.1 判定：**HEADER 那套可信**

三条独立理由：
1. **HEADER 的 `leaderFreqHz = 1899.91` 几乎精确命中 1900** ✓ 误差 0.005% ✓
   而标定头是**专门为频率标定设计**的（1900 Hz 长音 + 两个已知 VIS 频率）✓
2. **同步拟合的残差 20822 说明它没有拟合到任何东西** ✗ 其参数无意义 ✓
3. **+9.7% 的频率尺度与"时间轴正常"矛盾** ✗ 而 HEADER 的 −1.02% 与时间轴相容 ✓

**→ 解码器采用了不可信的那一套** ✗
**这是一个真实的优先级/质量门问题**：**前导阶段的拟合结果没有经过质量检查就被采用** ✓

### 4.2 但有一个我无法解释的残余
