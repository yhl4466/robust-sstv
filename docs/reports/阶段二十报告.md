# 阶段二十报告：真实 Scottie S1 录音解码失败的时序诊断

**结论（先给答案）**：**音频没有被变速，时序与音高都在标准位置。** 三项独立测量都指向这一点，
而且「按任意倍率重采样后重解」的实验证明——**只有 x1.00 能解码，其余全部直接失败**。

病灶**不在速度**，而**在行内部**（频率/像素估计），并且本轮定位出一条极有价值的结构性事实：
**这是我们第一次拿到真实的 Scottie S1 录音**（项目 L2 明确记录：检索六个公开仓库只找到 Martin M1 样本）。
自往返测试**在原理上无法发现**"编码器与解码器共同偏离标准"的错误。

---

## 1. 检测到的同步脉冲数量（报告第 1 项）

| 项 | 实测 |
|---|---|
| 1200 Hz 同步脉冲总数 | **589 个** |
| 期望脉冲率（S1） | 2.34 个/秒 |
| **规律脉冲区段（≥20 s）** | **0–104 s（273 个）**，**106–216 s（301 个）** |
| 帧数 | 文件 **220.152 s ÷ 110.643 s = 1.990 帧** |

**文件里有两段传输**，与"≈2 帧"的时长算术一致 ✓ 第 1 段只有 104 s（**不完整**——录音从一帧中途开始），
第 2 段 106–216 s 是**完整帧**。

**解码器锁定的是第 2 段**（自报 `imageStart = 5,133,600 采样 = 106.950 s`）——
`106.950 .. 217.593 s`，**这正好是那段完整的传输** ✓ **所以"锁错位置"不是病因。**

## 2. 行同步间隔（报告第 2 项）

| 统计量 | 实测 | 标准 S1 |
|---|---|---|
| **中位数** | **428.000 ms** | **428.22 ms** |
| **MAD（中位绝对偏差）** | **1.000 ms** | — |
| 均值 / 标准差 | 377.211 / 137.406 ms | — |
| 极值 | 5.00 .. 1529.00 ms | — |

**必须用中位数与 MAD，不能用均值**：均值被"音乐/噪声产生的假脉冲"拖低了 51 ms（标准差 137 ms）。
直方图显示一个**极紧的 428 ms 主簇**，外加一条 0–160 ms 的假脉冲长尾 ✓

**解码器使用的区段内部**：
```
该区段内 1200 Hz 脉冲数  : 300  (期望约 258 个)
该区段间隔中位数 / MAD   : 428.000 / 1.000 ms  -> 规整，是真实的行同步序列
```

**这是一个决定性的否定结果**：解码器锁定的区段**拥有教科书级规整的行同步序列**（中位 428.000 ms、
MAD 1 ms）。**同步没问题，区段没问题，图却是噪声** → 病灶在**行内部**。

## 3. 实际像素时间（报告第 3 项）

**先说一个必须纠正的数字**：你任务书里的"标准 S1 像素时间 **457.6 µs**"是**错的**。

| 模式 | scanTime | 每行通道数 | 像素时间 | 出处 |
|---|---|---|---|---|
| Martin M1 | 146.432 ms | 3 | **457.6 µs** | ← 457.6 是 **M1** 的值 |
| **Scottie S1** | **138.240 ms** | 3 | **432.0 µs** | ← **S1 正确值是 432.0** |

**项目内的错误出处**：`scripts/gen-tech-html.js:70` 写着「**逐行同步族的**像素时间为 457.6 µs」——
把 M1 的值安到了整个逐行同步族（M1 **和 S1**）头上 ✗
（`js/lib/sstv-decode.js:931` 与 `js/lib/sstv-modes.js:121` 里的 457.6 是**正确的**，
它们明确说的是 "Martin M1's 457.6 us"。）

**实测推算**：

```
行内非扫描开销 = sync 9 + porch 1.5 + 2 × sep 1.5 = 13.50 ms
像素时间 = (428.000 − 13.50) / 3 通道 / 320 像素 = 431.77 µs
标准     = 432.00 µs
偏差     = −0.053%
```

**我自己也犯过同一个错**：诊断脚本第一版把**整行时间**除以 320（忽略 3 个通道与同步开销），
算出 1337.5 µs、假的 −0.97% 偏差。已修正（`LINE_MS` 改为**逐行结构求和** 428.22 ms，
而不是 `totalDuration/height` = 432.20 ms——后者把 ~1 s 的前导/VIS 开销摊到了每一行）。

## 4. 与标准 S1 的偏差比例（R 值）（报告第 4 项）

| 量 | 实测 | 标准 | **R** |
|---|---|---|---|
| **行时间** | 428.000 ms | 428.22 ms | **0.99949** |
| **像素时间** | 431.77 µs | 432.00 µs | **0.99947** |
| **前导频率**（解码器自报） | **1899.914 Hz** | 1900 Hz | **0.99995** |
| 同步音频率 | 1200 Hz 上检出 MAD=1 ms 的规整串 | 1200 Hz | **≈1.000** |

**四项独立测量全部落在 1.000 ± 0.06% 以内** ✓

### 4.1 一处必须声明不可用的指标

我的 `[4]` 频率扫描报告 `R_freq = 0.8750`（最佳频率 1050 Hz）——**这个数字不可用**。
原因：打分函数 `score = 脉冲数 / (1 + 80%跨度)` **偏好"脉冲少而规整"**，而图象内容在 1050 Hz 附近
的**周期性图案**会造出又少又规整的假脉冲，于是压过了真正的 1200 Hz 同步音。
**可靠的频率证据是另外两项**：前导 1899.91 Hz（解码器自报）与 1200 Hz 上 MAD=1 ms 的 589 个脉冲。

### 4.2 决定性实验：重采样验证（把你的假设变成可证伪的测试）

按候选倍率把音频还原后重解，用**行间垂直相关**判断"像不像一张图"（真实图像相邻行高度相关，
噪声接近 0；该指标**不需要真值**）：

| 候选倍率 | 结果 | 行间相关 |
|---|---|---|
| x0.70 / x0.80 / x0.90 | **解码失败** | — |
| **x1.00（不缩放）** | **ok** | **0.2474** |
| x1.10 / x1.20 / x1.30 / x1.50 | **解码失败** | — |

**任何速度改变都会让情况变得更糟（直接解不出）。**

## 5. 判断：是变速？变体？还是频率映射问题？（报告第 5 项）

### 5.1 变速 —— **已排除**

三条独立证据：
1. R_time = 0.99949、R_pixel = 0.99947、R_freq(前导) = 0.99995
2. 重采样实验：**只有 x1.00 能解**，0.7/0.8/0.9/1.1/1.2/1.3/1.5 **全部失败**
3. 时长算术：220.152 s = **1.990 × 110.643 s**；若真变速 1.5×，两帧只需 147.5 s

### 5.2 变体（不同模式/非标准结构）—— **已排除**

594… 实测行时间 **428.000 ms** 与标准 S1 的 **428.22 ms** 完全吻合，
同步音在 **1200 Hz**、前导在 **1899.9 Hz**、像素时间 **431.8 µs** vs 432.0 µs。
**这不是某个变体，就是标准 Scottie S1。**
（另：解码器与 Robot36 都报 VIS 60，一致。）

### 5.3 **频率映射 / 行内部** —— **这是剩下的唯一方向**

依据链：
- 区段正确（106.95 s 起，完整帧）
- 区段内的行同步**教科书级规整**（428.000 ms / MAD 1 ms）
- 时序与音高都在标准位置
- **却解出 0.2474 的行间相关（噪声级）**

→ **误差发生在"行内"**：每个通道扫描窗内**哪里取像素、取到的频率如何映射成灰度**。

**另一个可疑信号**（需重测确认，见下）：解码器自报的仿射标定是
`scale = 0.9898` 与 `offsetHz = 19.27`。用这两个参数反推它认为的同步音频率：
`(1200 − 19.27) / 0.9898 = **1193.0 Hz**` —— 即它把真实同步音当成了 **1193 Hz**（偏低 0.58%）。
而实际同步音在 **1200 Hz**。**标定的两个锚点互相矛盾**（前导 1899.9 与它推断的 1193），
这通常意味着**同步频率的估计被图象内容/干扰带偏**，而不是音频真的偏了。

### 5.4 一条极有价值的结构性事实

**项目 L2 明确记录**：「检索六个公开仓库仅得到 **Martin M1** 样本；规格文档不可获取」——
也就是说 **S1 解码路径从未被真实录音验证过**，全部 S1 证据都是**自往返**（`roundtrip.js`）。
自往返**在原理上无法发现**"编码器与解码器共同偏离标准"的错误：两边共享同一个假设，往返必然自洽 ✓
**phigros 是第一次真实 S1 检验，而它失败了。**

## 6. 建议：下一步该加什么功能（报告第 6 项）

### 6.1 **不要做**自动速度检测

实测三次独立否决了变速假设。做自动速度检测是在**解决一个不存在的问题**，
而且从 [8] 的结果看，**任何速度缩放都会让解码直接失败**——引入它只会增加失败面。

### 6.2 **要做**（按优先级）

| # | 功能 | 理由 | 代价 |
|---|---|---|---|
| **1** | **行内仪器化 dump**：对指定若干行输出"同步位置 / 各通道窗起点 / 窗内频率估计 / 该像素的置信度"，并与用标准时序**手算的期望值**逐项对比 | 这是唯一能把"行内误差"定位到具体环节的手段。现在只能看到"结果是噪声"，看不到**哪一步**错 | 中（只加诊断输出，可放在 `diagnose-*.js` 里，不动解码器） |
| **2** | **接收报告**：把本轮已经算出来的量做成界面/脚本可读的报告（前导频率、行间隔中位数与 MAD、同步音频率、图象频带范围、标定 `scale/offset/clockScale`、锁定区段与时长） | 用户现在只能得到「解码失败」四个字，而这些数字**每一个都能直接指出病因**。这是把本轮成果产品化 | 低（数据已有） |
| **3** | **带限预滤波实验（1500–2300 Hz）** | 我的探针在图象窗里看到过 **2531 Hz** 的峰值（**高于白电平 2300 Hz**），提示存在带外干扰；若成立，一个廉价的带限滤波就能显著改善真实录音的解码 | 低（先做实验确认，再决定是否入产品） |
| **4** | **补真实 S1 素材** | L2 的根因是"没有真实 S1 样本"。phigros 已经证明自往返无法暴露 S1 的问题，**应把它固化为回归素材** | 低 |

### 6.3 需要声明的一处诊断缺陷

我的 `[4]` 频率扫描打分函数有缺陷（§4.1），报告的 `R_freq = 0.8750` **不可采信**。
第 3 项建议（带限滤波）所依据的"2531 Hz 峰值"也来自一个**窗长用错的探针**
（用了 42.7 ms 的窗去测 9 ms 的同步脉冲，`dur` 参数未生效），**必须先重测**再据此下结论。
我把它列为建议而非结论，正是因为它还没被可靠地测出来。


## 9. 顺带发现的文档错误（本轮未修，因它属生成物）

`scripts/gen-tech-html.js:70` → 生成的 `tech.html` 里写着：

> 「…逐行同步族的像素时间为 **457.6 µs**。」

**应为**：Martin M1 为 457.6 µs，**Scottie S1 为 432.0 µs**。
`tech.html:120` 的表格注释对 **PD 族**的像素时间（190 / 285 µs）是**正确**的，
错误只在于把整个逐行同步族都算成了 M1 的值。

修它需要改生成器并重新生成 `tech.html`，而本轮明确要求不改 `tech.html`，故只报告。
**注意这个错误数字已经外溢**：它出现在了你本轮任务书里（"标准 S1 的 …像素时间 457.6 µs"），
并被我第一版脚本沿用，进而算出过一个假的 −0.97% 偏差。
