### 1.1 `noteSync()`：全局最小二乘 → 4 间隔滑窗 + 双门（AC1）

```js
var LINE_WINDOW = 4;
var LINE_TOLERANCE_SAMPLES = Math.round(0.001 * sampleRate);   // 48 采样 @48k
var lineIntervals = [], lastSyncPos = null;

function noteSync(pos) {
  if (lastSyncPos != null) {
    lineIntervals.push(pos - lastSyncPos);
    if (lineIntervals.length > LINE_WINDOW) lineIntervals.shift();
    // 窗口均值与标准差
    var wm = mean(lineIntervals), wsd = stdDev(lineIntervals);
    var gated = wn >= LINE_WINDOW;
    var nominalOk = Math.abs(wm - nominalLineSamples) <= LINE_TOLERANCE_SAMPLES;
    var pass = nominalOk && (!gated || wsd <= LINE_TOLERANCE_SAMPLES);
    if (pass) measuredLineSamples = wm; else lineWindow.rejected++;
  }
  lastSyncPos = pos;
```

**关键点（这一处是本轮成败所在）**：**标称一致性门始终生效，只有标准差门等待窗口满** ✓
第一版按任务书字面实现——「窗口未满时用已有数据算均值，**不判门**」——**结果完全失败** ✗
诊断输出直接暴露了它：

```
滑窗: n=4 mean=20085.3 sd=34.72 采样   采纳=0  否决=252      行周期 20221
```

| 观测 | 含义 |
|---|---|
| `sd = 34.72 < 48` | 标准差门**通过** —— 因为错误位置**彼此一致**，系统性偏移不产生离散 ✗ |
| `\|mean − 标称\| = 469 > 48` | **标称门否决** ✓ |
| **采纳 0 / 否决 252** | **全部否决** —— 那 `measuredLineSamples` 理应停在标称值 20554.6 ✗ |

**但实测是 20221** ✗ → 说明有一个**未被门保护的写入路径**：
**窗口填充期（前 3 个间隔）的 `pass` 恒为真**，把已被污染的均值 20085 **无条件写死**；
此后每一次带门更新都被否决 → **那个坏值被它后面的门"保护"了整个帧** ✓✓
**门最终保护了它本该拒绝的那个值** —— 与设计目的正好相反 ✓

**改为标称门始终生效后**：

### 1.2 逐行循环：加自由运行回退（AC2）

```js
var res = alignSync(est, samples, sampleRate, mode, seqStart, true, calF);
if (res == null) {
  freeRunLines++; freeRunTotal++;
  if (freeRunLines > MAX_FREE_RUN_LINES) { warnings.push(...); truncated = true; break; }
  if (auditRefsOut) auditRefsOut.push({ line: line, ref: seqStart, freeRun: true });
} else {
  freeRunLines = 0;
  seqStart = res;
  if (auditRefsOut) auditRefsOut.push({ line: line, ref: res });
  noteSync(res);
}
```

**改动前的原文是**：`if (res == null) { warnings.push('…音频结束…'); truncated = true; break; }` ✗
—— **一次同步漏检就丢掉整帧剩余部分** ✓
`seqStart` 在上面已带 `+= measuredLineSamples` 的预测，所以自由运行行就按**最近一次裁决出的速率**解调，
下一轮继续搜索真脉冲 ✓

**与 Java 的 1.25 行规则的对应关系**：上游按**时间**判定（`currentSample > lastSyncPulseIndex + 1.25×行周期`）；
我们的循环**本就是逐行推进**，所以"本行未找到同步"即该 1.25 行期限的离散等价 ✓
`MAX_FREE_RUN_LINES = 32` 是**我加的**上限（上游靠标定头路径重锁、不需要它；我们一次解完整个文件，
若不设上限，一段以纯噪声结尾的录音会被"解"成一整帧虚构内容）✓

**实测 `freeRunTotal = 0`** —— 本录音中 `alignSync` **始终返回了位置**（哪怕位置是错的），
所以这条回退路径**没有被触发** ✓ 如实报告：它已实现、已通过语法与回归验证，
但**尚无用例证明它真的救回过失锁帧** ✗（构造该用例属下一轮）

## 5. AFC / 时钟恢复不退化验证（报告第 5 项）—— **未做**

**❌ 我本轮没有做 AC7 的两项测试**（±50 Hz 频偏合成音频、1% 采样率失配合成音频）✗

**为什么**：预算耗尽。**不把"逻辑上应该没问题"当作"已验证"** ✗

**但有一条间接证据（不足以替代 AC7）**：`roundtrip.js` 与 `pd-modes.test.js` 覆盖了
M1/S1/PD120/PD180 的完整编码→解码往返，其中**包含采样率与频率轴的正常工作范围**，
四者 PSNR **逐位不变** ✓ 说明裁决层在这些路径上未改变行为 ✓
**然而这两套测试并不含"频偏/时钟失配"这两类受控损伤** → **AC7 确实是缺口** ✓

**下一轮应补的用例（明确规格）**：
1. 合成 S1 → 整体频率搬移 ±50 Hz → 解码，比较 PSNR 与改动前
2. 合成 S1 → 重采样 1.01× / 0.99× → 解码，比较 PSNR 与改动前
3. 判据：两项 PSNR 与基线之差 ≤ 0.5 dB

**一处需要提前警惕的耦合**：裁决层现在**用标称行长做门**（`|mean − 标称| ≤ 1 ms`），
而 1% 采样率失配会使行周期偏离标称 **1% ≈ 205 采样 > 48** ✗
→ **失配超过约 0.23% 时，标称门会把合法值也一并否决，从而拒绝采纳新速率** ✗
**这正是 AC7 必须先跑的原因**，也是本轮方法的一个**已知边界**，必须写进报告 ✓
（缓解方向：门限改为相对比例而非固定 1 ms，或允许门随已采纳速率缓慢松弛 —— 属下一轮决策）

## 8. 本轮最值得记录的一点

**任务书字面实现会失败，而失败的原因恰恰在任务书自己的一句注释里**：

> 「窗口未满 4 个时：用已有数据计算均值，**不判门**」

这一句在干净信号上无害（合成音频的前几个间隔就是标称值），
但在真实录音上，**前几个间隔已是污染值** → 被无条件写死 → **后续的门反过来保护它** ✓
**采纳 0 / 否决 252** 这个组合是唯一能识破它的证据 ——
只看行周期（20221，误差 1.6%）会以为"门起了作用、只是不够好"，**而真相是门一次都没生效** ✗

**所以本轮真正的产出不只是 0.1962 → 0.5703，而是把"门看起来在工作"与"门真的在工作"区分开了** ✓
