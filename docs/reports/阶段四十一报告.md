## 3. R 槽采样起点的实测偏移（报告第 3 项）—— **偏差 0 px**

```
解码器 chanOffsets（scottie）: [G, B, R] = [base+chanTime, base+2·chanTime, base]
  base = syncPulse + syncPorch = 10.50 ms
  chanTime = sepPulse + scanTime = 139.74 ms
  => G 150.24 ms · B 289.98 ms · R 10.50 ms（相对同步）

标准布局 [sep][G][sep][B][SYNC][porch][R] 给出的 R 起点 = sync + porch = 10.50 ms
=> R 槽起点与标准一致 ✓ 偏差 0.00 ms = 0 px
```

**另核对我的探针与解码器的关系**：
```
我的探针 STARTS: G -277.98 ms · B -138.24 ms · R 10.50 ms
探针与解码器的 G/B 相差 428.22 ms = 恰为一个行周期（相位等价 ✓）
```
→ **探针与解码器的槽几何在相位上完全等价** ✓ **R 起点一致** ✓

**→ 结论：21 px（9.07 ms）的偏差【不在】R 槽的时间起点上** ✗✓
**"R 槽从 sync 开始（少算 9 ms）"这一候选被排除** ✓

### 4.2 仍可疑的代码位置（**下一轮排查清单**）

| # | 位置 | 为什么可疑 |
|---|---|---|
| **1** | **逐像素采样位置** `pos = seqStart + (chanOffsets[chan] + (px + 0.5) * pixelTime − centreWindowTime) * sampleRate` | **21 px 只可能来自这里**：`pixelTime`、`(px+0.5)` 口径、或 `centreWindowTime` 的符号 ✓ |
| **2** | **`pixelTime = nominalPixelTime × clockScale`**（`clockScale = 0.9898` 时像素时间偏 −1.02%）✗ | 320 px × 1.02% = **3.3 px** ✗ 量级不足 ✓ 但值得核对符号 ✓ |
| **3** | **`centreWindowTime` 的扣除** | 若窗口中心对齐方式在 G/B/R 上不一致，会产生**固定像素偏差** ✗ 与"21 px 恒定、MAD=0"吻合 ✓ |
| **4** | **R 槽的 `seqStart` 递推**（`seqStart += measuredLineSamples` 的时机）| 若 R 相对 G/B 多推进或少推进一次，会产生**接近一个行周期**的偏差 ✗ 不是 21 px ✗ |

**★ 最可疑的是 #3**：**MAD = 0（256 行完全一致的 21 px）** 指向一个**与行无关的固定偏移** ✓
而 `centreWindowTime` 是一个**对所有像素统一施加的常数** ✗
**若它在某个通道上的取值与其它通道不同，就会产生一个恰好恒定的像素偏移** ✓✓

### 4.3 建议的下一轮排查方法

**直接插桩打印真实采样位置** ✓（不改算法，只加临时代码或复用 `auditLineRefs` 钩子）：

1. 对**同一行**，分别打印 G、B、R 三槽**第一个与最后一个像素的实际采样索引**（`pos`）✓
2. 与**标准 Scottie S1 的期望位置**逐项相减 ✓
3. **G 与 R 的实际采样索引差**应为 `chanOffsets[R] − chanOffsets[G]` 加上像素项 ✓
   若差值比期望多/少 21 px → **偏差就出在 `pos` 的计算链** ✓
4. 同时打印 `centreWindowTime`、`pixelTime`、`windowFactor` 在三个通道上的值 ✓
   **若三者相同，则排除窗口项** ✓
