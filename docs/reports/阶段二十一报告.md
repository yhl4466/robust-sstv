## 2. 差异表的分析结论（报告第 2 项）

```
截距     -0.223 采样 = -0.011 像素   -> 近似为 0：同步定位没问题
斜率     -0.44543 采样/像素
末像素累计 -142.1 采样 = -6.85 像素
R²       1.0000   残差标准差 0.00 采样
```

| 观测 | 结论 |
|---|---|
| 截距 ≈ 0 | **同步定位准确**（不是"所有像素偏 N 个采样"） |
| 斜率恒定、R²=1.0000、残差 0 | 偏差**完全线性累积** —— 正是"像素时间/时钟尺度"误差的作用方式 |

### 2.1 必须声明：这个回归是**同义反复**的

两套网格都是**我在脚本里算出来的**，唯一差别就是我喂进去的 `clockScale`（0.97852 vs 1.0）。
所以 `R² = 1.0000` 与 `残差 = 0` 是**构造上必然成立**的，它**不能**证明解码器的网格错了。

它**能**说明的只有一件事：**若 `clockScale` 真为 0.97852 而真实值为 0.99949，则一条行末会累积
6.85 像素（142 采样）的横向错位** —— 这是一个**量级**陈述，不是因果证明。

### 2.2 dump 里真正非平凡、且指向根因的发现

**逐像素频率估计落在 3.0–3.4 kHz**，而 SSTV 图象频带是 **1500–2300 Hz** ✗

原因链条（可从代码读出）：
- 像素窗只有 **51 采样 = 1.06 ms**（`scanTime/width × windowFactor 2.48 × 48000`）
- 该窗长下 FFT 尺寸被钳到最小值 **128** → bin 宽 **375 Hz**（频率分辨率极粗）
- 而峰值搜索**覆盖全频带**，没有任何带限约束

→ 1 ms 窗 + 全频带取峰，**最强的那个东西未必是图象音**。实测它落在 3 kHz 附近，
于是 >2300 Hz 一律钳为白 → 输出饱和噪声 ✓

## 3. 标定参数矛盾的根因（报告第 3 项）—— **我上一轮错了**

### 3.1 独立测量（短窗修正后，分辨率已校验）

```
傅里叶分辨率检查: 同步窗 240 采样, 零填充到 8192 点 -> 5.86 Hz/bin
前导音（150 ms 长窗）      : 1899.39 Hz   标准 1900   解码器自报 1899.914
同步音（5.0 ms 短窗, n=24）: 1195.31 Hz   标准 1200   置信中位 0.1 dB
解码器反推的同步音         : 1192.88 Hz   (由 a=0.9898 b=19.27 反解)
=> 前导偏差 -0.032%   同步偏差 -0.391%
```

### 3.2 结论：**没有矛盾，标定是正确的**

| 量 | 独立实测 | 解码器 | 一致性 |
|---|---|---|---|
| 前导音 | 1899.39 Hz | 自报 1899.914 Hz | 相差 0.5 Hz ✓ |
| 同步音 | **1195.31 Hz** | 反推 **1192.88 Hz** | 相差 **2.4 Hz**，**小于 5.86 Hz 的 bin 宽** ✓ |

解码器的仿射标定用两个锚点（前导 1900、同步 1200）解两个参数（a、b），
而**这段录音的同步音本来就在 1195 Hz 附近**（比标称低 0.39%），前导却在标称位置。
两个锚点因此**一致地**确定了 `a=0.9898, b=19.27` ✓ **这是正确拟合，不是矛盾。**

### 3.3 「1200→1193」这个说法为什么错

上一轮我检测同步脉冲的方式是**在 1200 Hz 上做包络检测** —— 那只能证明"这个频率上有能量"，
**不能测量该音调的实际频率**。我却据此断言"实测同步音就是 1200 Hz"，进而把解码器的
1193 Hz 当成锚点矛盾 ✗ **这是我的推断错误，已在上一轮报告基础上更正。**

**至于"为什么会有 0.39% 的偏差"**：前导正常而同步偏低 0.39%，**不是**均匀的频率偏移
（那会让两者同比例变化），更像录音/播放链路上的局部失真。但它**不影响**解码——
标定已经把它换算掉了（§B 实验也证明关掉标定并不改善）。

## 5. 四组对照解码 + 带限实验（我为验证根因加的实验）

### 5.1 四组对照（全部用**已有公开选项**，未改解码器）

| 变体 | clockScale | a | b | 行间相关 |
|---|---|---|---|---|
| 基线（默认） | 0.97852 | 0.98981 | 19.27 | **0.2474** |
| **关时钟恢复** `{clockRecovery:false}` | **0.97852 ← 未变** | 0.98981 | 19.27 | 0.2479 |
| 关频率标定 `{afc:false}` | 0.97852 | **1.00000** | **0.00** | 0.2479 |
| 两者都关 | 0.97852 | 1.00000 | 0.00 | 0.2483 |

**两条结论**：

1. **`afc:false` 生效（a=1,b=0）但图完全没改善** → **频率标定不是病因** ✓
   （这也再次印证 §3：标定本身是对的，关掉它当然也没用。）
2. **`clockRecovery:false` 无效** —— `clockScale` 仍是 0.97852 ✗
   `sstv-decode.js:310` 在 `!clockRecovery` 时设 `calib.clockScale = 1`，
   但 `:881` 又执行 `calib.clockScale = measuredLineSamples / nominalLineSamples` **覆盖了它**。
   **这是一个解码器缺陷**（选项名与行为不符）。因此**本轮无法验证 `clockScale` 假设** ——
   如实报告，不宣称已验证；修它属改算法，本轮不做。

### 5.2 带限实验（**结论不可用，方法有缺陷**）

| 带限 | 行间相关 |
|---|---|
| 1400–2400 Hz | 0.0487 |
| 1000–2600 Hz | 0.0485 |
| 1200–2400 Hz | 0.0300 |

全部**比不滤波（0.2474）更差**。原因是我用了**二阶 IIR biquad**，而：
- 1400 / 1200 Hz 的**高通直接把 1200 Hz 同步音削掉了** ✗ 同步路径被破坏
- 即便 1000–2600（保留了 1200）也变差，说明二阶 IIR 的相位响应足以伤害解调

→ **这个实验不能用来判断"带外干扰是否存在"**，因为工具本身引入了更大损伤。
**必须改用线性相位 FIR 重测。** 我把它列为"未完成"，不据此下结论。

## 8. 对 S1 解码失败的最终判断（报告第 7 项）

### 8.1 已被**测量**排除

| 假设 | 排除依据 |
|---|---|
| 音频被变速 | 上一轮：R_time 0.99949、R_pixel 0.99947、前导 R 0.99995；且任意倍率重采样后**全部解码失败** |
| 是别的模式/变体 | 行时间 428.000（标准 428.22）、同步音 1195、前导 1899.4、像素 431.8 —— 全部落在标准 S1 附近 |
| **频率标定错误** | **本轮**：`afc:false` 生效（a=1,b=0）而行间相关 0.2479 vs 基线 0.2474 —— **毫无改善** |
| 标定锚点矛盾 | **本轮推翻**：独立实测同步音 1195.31 Hz，解码器反推 1192.88 Hz，**在 bin 宽之内一致**（§3） |
| 同步定位错误 | dump 截距 −0.22 采样（≈0.01 像素）；且区段内 300 个脉冲、中位 428.000、MAD 1 ms |

### 8.2 **未能验证**的假设（如实声明）

**`clockScale = 0.97852` 的误拟合** —— 它**看起来**最像元凶（2.1% 误差 × 整条行的像素网格 =
行末累积 6.85 像素），但：
- `clockRecovery:false` **无效**（§5.1，解码器缺陷），我**无法**把它置为 1 来做对照
- 而 §2.1 的回归是同义反复，**不能**作为它错了的证明
→ **该假设既未被证实、也未被排除。** 这是本轮最大的遗留。

### 8.3 数据支持的**剩余机制**（最可能的根因）

**逐像素频率估计落到了图象频带之外**：

| 环节 | 实测/代码 |
|---|---|
| 像素窗长 | **51 采样 = 1.06 ms**（`scanTime/width × windowFactor 2.48 × 48000`） |
| 该窗长下的 FFT | 被钳到最小 **128 点** → bin 宽 **375 Hz** |
| 峰值搜索范围 | **全频带**，无带限约束 |
| **实测估计值** | **3003.5 / 3018.2 / 3348.6 / 3365.9 Hz**（10 个抽样里 7 个 > 2900 Hz） |
| 后果 | `calcLum` 把 >2300 Hz 一律钳为 **255** → 灰度全白 → **高饱和噪声** ✓ |

**即：1 ms 窗 + 全频带取峰，使估计器锁到了图象音之外的内容；而 SSTV 的灰度判据完全依赖
"频率落在 1500–2300 Hz 之间"，一旦越界就饱和成白。** 这解释了"几乎纯噪声、顶部有横向结构"
（顶部少数行恰好落在带内，故有结构）✓

**注意**：这一机制**不等于**"音频里有干扰" —— 也可能是**估计器本身的窗口/带宽设计**在真实录音的
噪声条件下失稳。要区分两者，需要 8.4 的第 1 步。
