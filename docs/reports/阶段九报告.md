| 项目 | 实现 |
|---|---|
| 浏览器探测 | 四条路径（Edge x86/x64、Chrome x64/x86） |
| 启动 | `--headless=new --disable-gpu --hide-scrollbars --force-device-scale-factor=1 --remote-debugging-port=9341`，`stdio:'ignore'` |
| 端口 | **9341**（`browser-e2e.js` 用 9333，两者可同时运行） |
| 布局宽度 | `Emulation.setDeviceMetricsOverride({width:1280})`，并**回读断言 `clientWidth === 1280`**，不满足即报错退出 |
| 被测对象 | **`tech.html` 本身**（出货件），而非副本 |
| 坐标系统 | 统一映射到 **viewBox 用户单位**：`vb.x + (clientX − svgRect.left) / scale` |

**为什么不用 `getBBox()` 作主判据**：它返回元素**自身局部坐标系**的盒子，遇到 `transform="rotate(-90 …)"`（图 7–10 的纵轴标签）就与 viewBox 对不上。`getBoundingClientRect()` 是**渲染后的真实外接矩形**（含描边、含变换），反算回 viewBox 即"视觉上占据了哪里"。`getBBox()` 仍并行记录，用于核对。

### 一次我自己的严重失误（已修）

首轮我曾看到这样的输出：

```
tech.html measured: 0 SVGs at 1280 px layout width
totals: {...} -> 0 issue(s)
```

**"0 张 SVG" 却报 "0 问题"** —— 测量为空时所有计数自然为零，这是一次**假绿**。根因是我用固定 `sleep` 等页面加载，`Runtime.evaluate` 落在了 `Page.navigate` 之后的过渡空文档上。修法有两处，缺一不可：

1. 改为**轮询** `document.querySelectorAll("svg").length === 10`（15 s 超时），不再依赖 sleep；
2. **断言数量**：不足 10 张即抛错，绝不进入统计。

这条值得单独记录，因为"空输入导致零告警"是任何检查工具最危险的失效模式。

### 2.2 字号过小（80 项）：根因不是字号，是**图形被缩小了**

分布：fig7 13、fig9 23、fig6 9、fig8 9、fig3 8、fig2 6、fig4 5、fig10 5、fig1 2、fig5 0，全部为 `11px → 9.66px`（fig6 另有 6 项 `10px → 8.78px`）。

**根因**：`.paper` 正文栏 `max-width: 1080px`，留给一幅 1200 单位宽的图的只有约 1054 px，于是整张图被缩放到 **scale 0.878**，11px 标签实际渲染 **9.66px**。

**因此正确修法不是把 80 处字号调大**（那要改 80 个位置并引入新的溢出风险），而是**让图形按原尺寸突破正文栏**——图形本来就比正文栏宽，这是学术排版的标准做法。

## 9. 遗留与建议

1. **体检工具不含"文字 vs 图形"检测**：本轮的 2 处真实缺陷都属这一类，是靠目视发现的。若要补第 6 类，可行做法是把 `<line>` / `<polyline>` 的线段与每个 `<text>` 盒做相交判定（对旋转线段需先离散采样）。
2. **`image-pages-e2e.js`**：已通过（28 项），无遗留。
3. **fig9 组名中英混排**：属论文内容范畴，本轮未改。
4. **窄视口下仍会缩小**：本轮把 scale 修到 1.000 是在 1280px 视口下；视口更窄时 `max-width: calc(100vw - 24px)` 会让图形按比例缩小，届时 11px 标签可能再次低于 10px 有效像素。这是有意的取舍（不产生横向滚动条），如需覆盖需为该断点另调字号。
