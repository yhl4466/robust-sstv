## 4. 黑边修复前后的 unreachableFrac 对比（AC3）

### 4.1 病因定位：不是黑边，也不是动态范围，而是 embedder bug

先做定位（`diagnose-unreachable.js`），得到的关键样本：

```
line=  0 blk= 0 bit=1 min=0 max=0 mean=0  range=0  achievableWidth=255
```

**一个全黑、零动态范围、可达宽度满分的块，却判定为"不可嵌入"。** 这直接推翻了两个假设：
- **不是黑边跨块**：块是**水平**的（1 行 × B 像素），而黑边是上下两条水平黑带，**块不可能跨越它**；整块全黑时可达均值范围是 [0,255]，本该完全可嵌入。
- **不是动态范围**：`achievableWidth=255`。

**真实原因**：`targetFor(mean=0, bit=1, Δ=12)` 在正确奇偶格上取最近电平，而 **+12 与 −12 等距**，旧代码的等距判据选了 **−12**（越界）。于是 `diff = −192`、每像素 `can = v = 0`，**真的放不下**。
**影响面**：任何含纯黑行（或任何"最近正确电平落在钳位侧"的块）的图都会被系统性误判。E/F 类恒定 **3.13%**（= 16 行黑带 × 20 块的一半，即 bit=1 的那一半）就是它的指纹。

**修复**：`targetForBlock(mean, bit, delta, mn, mx)` —— 用块的 min/max 算出**真实可达均值区间** `[mean−mn, mean+(255−mx)]`，只在区间内选正确奇偶电平；两个候选都不可达时才如实标为不可达。

|---|---|---|---|

- **bug 造成的那个"每张图恒定 3.13% 地板"已被彻底消除**（E/F/C-0 降到 0.00%）✓

## 9. 事故留档：我自己造成的 app.js 编码损坏

**发生了什么**：我用 PowerShell `Get-Content -Raw | Set-Content` 往返修改 `js/app.js`（为替换两处标识符）。PowerShell 5.1 的 `Get-Content` 按 **ANSI(GBK)** 解码无 BOM 的 UTF-8 文件，`Set-Content` 再编码回去，于是：
1. 全部中文变成乱码；
2. **凡是无法映射到 GBK 的多字节序列，丢失一个字节**；
3. 丢失的字节常常**吃掉字符串的闭合引号**，文件不再能解析（95 处）。

**修复过程（三次尝试，前两次失败，都已留档在脚本注释里）**：
1. **编码逆变换**（`GBK.GetBytes` → `UTF8.GetString`）——**成功恢复全部中文**，但丢字节的空洞仍在。
2. **"统一补句号"** ——**失败**：丢的字符是 `数/帧/率/图/，` 等各不相同，产生了 `实际码字。/ 深度` 这类错误文本。
3. **"按行引号奇偶性判定"** ——**失败**：调用参数里的引号（`$('encStatus')` 贡献两个）破坏了奇偶计数。
4. **"按空洞后紧跟的字符判定"** ——**成功**（串内 48 处 / 补回引号 47 处），随后用显式替换表恢复具体标签。最终 **U+FFFD 空洞 0 个，文件语法通过，E2E 全绿**。

**已留档**：`js/app.js.corrupt`（原始损坏件）、`scripts/repair-appjs*.js`（三次尝试的规则与失败原因）。
**教训（已写进脚本注释）**：**本项目所有 JS/HTML/CSS 文件一律不得用 PowerShell 的 `Get-Content`/`Set-Content` 往返修改**；之前的 `eval-content.js` 也是同一个原因损坏的。
**影响面**：仅限 `app.js`（UI 层）。**测量与算法代码（`payload-qim.js`、`fec-rs.js`、`interleaver.js`、`sstv-*.js`）从未经过此路径，未被污染。**

## 10. 对"是否还需要 LDPC"的最终判断

**维持并强化结论：severe 档超出本方案适用范围，LDPC 不是它的解药。**

| 信道档 | B=32 下的实测 | 是否需要 LDPC |
|---|---|---|
| clean | 无 FEC 即 **100%** | 不需要 |
| **mild** | FEC 开 **100%**（goodput 215 B） | **不需要** |
| moderate | 无 FEC 即 **100%** | 不需要 |
| **severe** | **24 格全 0%**；字节正确率仅 24.7% | **需要，但不值得** |

**severe 的定量论证**：字节正确率 24.7% ⇒ 字节错误率 75%，远超任何硬判决码的能力；要让码率降到能覆盖这个错误率，可用载荷会掉到个位数字节。**这不是一个可用的传输方案**，把它写进结论比用 LDPC 硬撑更诚实。

**本轮新增的一条建议**（取代"考虑 LDPC"）：
> **当前最大的可靠性杠杆不是编码，而是"选图 + 选 B"。**
> 修复 embedder bug 后，同一 clean 信道上不同图源的 BER 相差 **76 倍**（E 2.15e-3 vs D 1.64e-1）；
> 而 B 从 16 加到 32 让 clean/moderate 在**无 FEC** 下就到 100%。
> 所以优先级应是：① 用面板预检挡掉不适合的图；② 定 B=32；③ 保持 RS。
> **只有当某个必须支持的图源类（如 D 卡通）在 B=32 + RS 下仍不达标时，才值得上 LDPC。**
