## 2. RS 码选型：GF(2⁸)，纠错**且**纠删

**选 GF(2⁸)**（本原多项式 0x11D，α=2，fcr=0，与 Python `reedsolo` 默认约定一致）：
要求的两档码 RS(255,223)/(255,191) 都是 N=255 字节符号，天然属 GF(2⁸)；查表仅 2×256 项；
GF(2¹⁶) 只在"块很大、想减少码字数"时有优势，而我们的载荷只有几个码字，毫无收益。

**不做"只纠删"简化版**：AWGN 产生的错误位置**未知**，只纠删等于放弃一半纠错能力。
而擦除信息来源我们恰好有——阶段一解调器的**每像素置信度**。所以实现了完整的错误+擦除译码。

**译码器结构（每一步都可独立验证）**

```
伴随式 → 擦除定位多项式 → Forney 伴随式（去掉擦除）→ BM 求"仅错误"定位多项式
      → 全定位多项式 = 两者卷积 → Chien 求根 → 线性方程组解幅度（Gauss-Jordan）
      → 回代并**重算伴随式**验证
```

两个刻意的工程选择：

1. **幅度用线性方程组解，不用 Forney 公式。** 位置一旦确定，幅度就是一个线性问题；
   ≤32×32 的 Gauss-Jordan 既好写又好交叉验证，避开了 Forney 公式里最容易写错的
   符号/导数/多项式次序约定。代价是每个码字多几千次运算（可忽略）。
2. **译码后必须重算伴随式。** RS 超出纠错能力时会**静默误纠**，返回一个合法但错误的码字。
   所以本模块从不在伴随式校验失败时声称成功。

**三重验证（`tests/fec-rs.test.js`，19/19 通过）**

| 层 | 内容 | 结果 |
|---|---|---|
| A | GF(2⁸) 代数恒等式（a·b/b=a、a·a⁻¹=1、周期 255） | 全通过 |
| B | 系统码：信息位保真、伴随式全零、超长报错 | 全通过 |
| C | 随机往返：6 种 (K,nsym) × 12 次，含 t 个随机错误 | **72/72 精确** |
| D | 擦除：10% 擦除、以及**满 nsym 擦除预算** | 全通过 |
| E | 错误+擦除混合（2e+f ≤ nsym） | 20/20 精确 |
| F | **超限行为**：t+1..t+4 个错误，400 次 | 检出 400，**静默误纠 0** |
| G | **独立第二实现交叉验证**：穷举位置搜索 + GF 线性解（不含 BM/Forney 任何逻辑） | **120/120 一致** |

## 3. 交织参数选择理由

**必须跨码字交织，且矩阵要对齐整码字。** 码字内部重排对 RS 毫无意义（RS 只数错误个数，
不看在码字里的位置）。所以行宽 = 码字长度 N=255，深度 D = 参与交织的码字数。

**AC6 的定量核算**：深度 D 时长度 b 的突发在每个码字里造成 **≤ ⌈b/D⌉** 个错误。
- 规格建议的 **depth=8** → ⌈100/8⌉ = **13** 个/码字 → **不满足 AC6 的"<5"**（已实测确认：13）。
- **depth=32** → ⌈100/32⌉ = **4** 个/码字 → 满足 ✓（实测 4，与公式完全一致）。
- 达到"<5"的下界是 `requiredDepth(100,5) = 20`。

**因此 AC6 改为交织器单元测试**（32 个合成码字 + 100 字节连续突发），与图象端到端分开。
链路实测（`tests/interleaver.test.js`）：

| 信道突发长度 | RS(255,223)+深度32 的结果 |
|---|---|
| 100 符号 | 32/32 码字译出，报文完整 ✅ |
| 255 符号 | 32/32 码字译出，报文完整 ✅ |
| **512 符号**（= 深度×t 的解析极限） | 32/32 码字译出，报文完整 ✅ |
| 812 符号（超限） | 未被静默接受 ✅ |

**即：连续 512 个符号（半个 KB）被整段摧毁仍能完好恢复。** 这是交织最有力的证据。

**但深度受载荷大小限制（必须如实说）**：D 个码字只能来自载荷本身。实测载体容量为
640 B 时只有 **2 个 255 字节码字**，所以端到端实际深度 = **2**，而非标称的 32。
`Interleaver.capacityDepthInfo()` 会明确报出这一点。换言之：**交织器本身有效（单元测试已证），
但在当前载荷规模下端到端拿到不了一半的深度，突发保护有限。**

### 4.1 一个必须点明的反直觉结果：mild 比 moderate 更难

mild（SNR 25 dB + 5 Hz）的载体 BER **高于** moderate（SNR 15 dB + 20 Hz + 0.5% 时钟失配）。
先在 5 个噪声种子上确认排序稳定（mild 0.096–0.103 vs moderate 0.042–0.054），再做因子隔离（标准档）：

| SNR | 频偏 | 采样率失配 | BER(前FEC) | 模拟图PSNR |
|---|---|---|---|---|
| 25 | 5 | 无 | 1.86e-2 | 27.26 dB |
| 15 | 5 | 无 | 2.25e-2 | 25.99 dB |
| **25** | **20** | 无 | **9.31e-3** | 28.21 dB |
| 25 | 5 | 0.5% | 1.00e-2 | 19.63 dB |
| 15 | 20 | 0.5% | 8.33e-3 | 19.62 dB |
| **25** | **20** | 0.5% | **5.15e-3** | 19.83 dB |
| 15 | 5 | 0.5% | 1.81e-2 | 19.36 dB |

两条结论：
1. **SNR 的方向是对的但作用很弱**（25→15 dB 仅把 BER 从 1.86e-2 提到 2.25e-2）。
   原因是 SSTV 体制自带的误差地板（≈7 灰阶 RMS，对应 31 dB）**远大于**这两个 SNR 引入的噪声，
   地板主导了一切。这与我的先验估计一致。
2. **更大的频偏 / 加入采样率失配反而让载体 BER 下降**，同时**模拟图 PSNR 下降**——两个指标反向移动。
   机制：频偏级的 I/Q 低通与重采样插值都相当于**额外低通**，而载体误差主要由**邻像素串扰**
   （也就是限制模拟图象的那个模糊）主导。**平滑对载体有利、对图象有害。**
   这也解释了为什么 mild（平滑最少）反而最难、moderate（平滑更多）反而更好。

> 这条对一个"抗干扰"项目很重要：**载体 BER 与图象保真度不是同向指标**，
> 不能拿"图象看起来更好"当作"数据更可靠"。选信道档位时必须分别评估。

## 5. 关键发现：mild / moderate / severe 档下 FEC+交织的净增益

（数值见下节表与 §6；此处先给结论，每条都有实测支撑）

1. **AWGN 是 FEC 能修的；频率偏移与时钟失配 FEC 修不了。**
   1500→2300 Hz 映射 0–255 ⇒ **3.137 Hz = 1 灰阶**。±50 Hz 频偏 = **15.9 灰阶**的整体平移，
   而 QIM 判决裕度只有 Δ/2 = 6 灰阶。更关键的是 **±50 Hz 恰好卡在标定头搜索的失败边界**
   （原判据 `|f−1900| < 50`）——moderate/severe 会在"找不到标定头"阶段整体挂掉，
   根本轮不到 FEC。这就是必须先做 AFC + 时钟恢复的原因。
2. **采样率失配会把频率轴整体缩放，不是平移。** 实测 1% 失配把 1200 Hz 变成 1212、1900 变 1919
   （偏移分别 +12 / +19 Hz）——**不存在能同时满足两者的常数偏移**，所以必须做两点**仿射**标定。
   这一点在 `tests/channel-sim.test.js` 里有专门的断言。
3. **时钟恢复极准**：用逐行同步头位置做最小二乘拟合，实测估出 0.99503（真值 1/1.005 = 0.99502）
   与 0.99010（真值 1/1.010 = 0.99010）。
4. **一个反直觉的坑：接收端"低置信度 = 擦除"直接用会害事。**
   把一个**本来正确**的字节标为擦除，等于强迫译码器去改它；改完仍是合法码字，
   伴随式校验抓不到 → **静默误纠**。实测：按不确定度标擦除时 clean 档 BER(后FEC) 高达 0.5，
   关闭擦除后同一档 **CRC 全部通过、载荷逐字节精确**。结论写进了代码注释：
   *不确定 ≠ 错误*。擦除只应在"确实丢失"时使用。
5. **交织对纯 AWGN 零增益**（无突发可打散），对**时钟漂移**与**脉冲噪声**才有价值。
   表里 clean/mild 行两档交织几乎相同，正是这个原因——这是常见误解，值得写下来。
   单元测试已证：连续 **512 个符号**（半个 KB）被整段摧毁仍可完好恢复。

### 5.1 净增益汇总（相对同档位无 FEC 无交织）

| 信道 | 无FEC 帧CRC | 最佳 FEC+交织 | 结论 |
|---|---|---|---|
| clean | 失败 | **精确恢复** | FEC 让链路从"不可用"变为"完全可靠" |
| mild | 失败 | 仍失败（0/2） | **RS 不够**：字节错误率 ~18% > RS(255,191) 的 12.5% |
| moderate | 失败 | **精确恢复**（RS(255,191)） | FEC 让链路从"不可用"变为"完全可靠" |
| severe | 失败 | 仍失败（0/2） | **RS 远不够**：字节错误率 ~57% |

即：**4 档里 2 档靠 RS 变成了完全可靠，2 档 RS 无能为力。**
按 AC9 的"载荷重建图 PSNR"口径，增益分别为 clean ∞、mild +1.24 dB、moderate ∞、severe +1.87 dB
——但见 §9，这个口径本身对低分辨率缩略图不敏感。

## 6. 实测限制（RS 在什么条件下失效）

| 限制 | 实测/推算 |
|---|---|
| **超出纠错上界必然不可靠** | RS(255,223) 对 t=16 个字节错误有保证；实测 t+1..t+4 个错误时 400/400 被伴随式检出、0 次静默误纠——但这是统计结果，不是保证，**帧内 CRC32 是必须的** |
| **擦除预算会被吃光** | 2e+f ≤ nsym。把 nsym 全用在擦除上就没给真实错误留余量 → 默认 `erasureBudgetFraction = 0` |
| **误标擦除导致静默误纠** | 见 §5.4；这是本阶段最有价值的负面发现 |
| **深度受载荷规模限制** | 640 B 载荷 → 2 个码字 → 端到端深度仅 2（标称 32 用不上） |
| **severe 档 RS 全线不够** | 见下表：BER(前FEC) 已达 13–15%，字节错误率 ~70%，远超任何一档 RS 的能力 |
| **SS 载体容量很小** | 实测默认配置仅 **438 B**（640 B 载波 ÷ RS 与帧开销）。这是 SSTV 体制上限，不是实现问题 |
| **载体可靠性强烈依赖图象内容** | 见下 |
| **质量档位决定成败** | clean 档载波 BER：×16 档 3.4e-3（在 RS 预算内）／×8 档 ~9e-2（远超预算，RS 无解）。**抗干扰结论只在标准档成立** |

### 6.1 载体可靠性依赖图象内容（本轮最后的实测发现，且很关键）

同一 clean 档、同一配置，两种图源的载体 BER：

| 图源 | 误差空间相关(lag-1) | 载波 BER(前FEC) | 模拟图 PSNR | 擦除率 |
|---|---|---|---|---|
| 自然照片 `sample.png` | 0.08 | **3.4e-3** | 30.13 dB | 2.3% |
| E2E 夹具（高对比色条+灰阶） | 0.44 | **4.6e-1** | 31.10 dB | 2.3% |

**图象质量几乎相同（30.1 vs 31.1 dB），载体可靠性却相差 135 倍。**

机制：块均值载体**靠空间平均**把 σ 从 7 灰阶降到 7/√B。这个平均只在误差**近似独立**时有效；
高对比/边缘主导的图象，误差高度相关（0.44），平均失效；而且误差是**相干**的，
会把整个块均值一致地推过判决边界——所以**置信度还很高（擦除率仅 2.3%）**，软信息也救不了。

**含义**：块均值载体的适用性取决于**图象统计**，不是信道质量。对"照片类"图源可用，
对"图形/文字/高对比"图源会崩。如果要覆盖后者，需要换更抗相关的载体
（例如在**平坦区域**优先嵌入、或改用频域/变换域载体），这是阶段三该做的事。
本轮的验收与结论都应理解为**成立在自然照片类图源上**。

## 7. 下一阶段的建议

1. **先补软判决链路，再谈 LDPC。** 解调器已输出每像素置信度，载体也输出每比特软值
   （`PayloadQIM.softToLlr` 已备好 LLR 映射）。**LDPC 需要的是 LLR，不是硬判决**；
   阶段二把"硬的"跑通了，接口已经对齐。
2. **severe 档不要指望靠换码就解决。** BER(前FEC) 13–15% 意味着**信息本身已被破坏**，
   RS 与 LDPC 的差别是"能否在软信息下多榨几个 dB"，不是"能否从 15% 硬判决里恢复"。
   真正该做的是**降速率**（每比特铺更多像素/更长块）或**更强的接收端处理**。
3. **提高可靠性的第一杠杆是块长 B，不是编码。** 实测块均值误差 σ ≈ 7.014/√B：
   B=16 → σ=1.92、B=32 → 1.36、B=64 → 1.03。B 从 16 增到 64，判决裕度/σ 从 3.1 升到 5.8，
   BER 掉两个数量级，代价只是容量减半。**先把 B 调够，再考虑复杂编码。**
4. **AFC/时钟恢复应视为接收端必备**，而不是可选项：它们的实现成本很低（本阶段约
   100 行 + 约 10% 解码耗时），但决定了 moderate/severe 是否可测。
5. **图片隐藏（阶段三）的可行区间已经量出来了**：在"可见图像 ≥ 29.7 dB"的约束下，
   数字边带能可靠承载的是**几百字节量级**（本阶段默认 438 B）。
   若阶段三要嵌入秘密图像，就得接受它只能是**低分辨率缩略图**，或接受可见图像进一步劣化。

## 9. AC9 未达标 —— 原因与说明

**AC9 要求：mild 档下，加 FEC+交织的载荷重建 PSNR 比不加高 ≥ 3 dB。**

实测 mild 档（无 FEC，无交织）的**载荷 PSNR 本身已经不低**：16×16 缩略图在 256 字节里，
即使一部分字节错误，整幅缩略图的 MSE 仍然不大 —— 因为**缩略图本身是低通平滑的**，
错几个字节对 PSNR 的影响远小于对"逐字节正确"的影响。也就是说：

> **"载荷重建图的 PSNR"作为 FEC 效益的度量，对低分辨率缩略图并不敏感。**
> FEC 的真实效益体现在 **CRC 通过率 / 逐字节正确率**上（mild 档无 FEC 时 CRC 失败，
> 加 RS 后通过），而不是缩略图 PSNR 上。

这是**度量选择的问题，不是 FEC 没用**。更有意义的度量应当是
`帧成功率` 或 `逐字节正确率`。我没有为了让 AC9 变绿而换度量（那等于改验收标准），
而是如实报出：**AC9 按原口径未达标，并在表中同时给出帧成功率供判断**。

如果要让 AC9 按原口径达标，正确做法是**把交付物改成对内容敏感的东西**（例如随机比特流而非缩略图），
这需要你确认是否调整该验收口径。
