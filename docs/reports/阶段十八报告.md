# 阶段十八报告：隐藏载荷在转码后能否提取 —— 实测与修复路线评估

**总体状态**：**结论与上一轮的预判相反 —— 隐藏载荷在正常情况下能挺过转码。**
9 个用例中 **7 个成功**（秘密图与原生 WAV **逐字节一致**），2 个失败。
本轮**未改任何算法**（AC5 ✓），只做验证与评估。**AC1–AC6 全部达标。**

> 上一轮我写的是「载荷从图象域量化块均值读出，比重采样敏感得多，**很可能失败**」。
> **实测推翻了这个预判。** 下面给出它为什么不成立，以及它在什么条件下确实会失败。

## 2. 失败模式分析（报告第 2 项）

**实测只出现了一种失败模式：C。A 与 B 一次都没有出现。**

| 模式 | 出现次数 | 说明 |
|---|---|---|
| **A 标定头检测失败** | **0** | 即使 Opus 16k 这种破坏性编码，公开图仍然解出来了 |
| **B VIS 识别失败** | **0** | 同上 |
| **C 公开图解出但载荷 CRC 失败** | **2**（m4a 32k、webm 16k） | `reason: 数字边带帧校验失败：bad magic (0xc9 / 0x24)` |
| **D 载荷部分解出、RS 能力不足** | **0** | 由于全部载荷只承载在**一个码字**上，RS 只有"全对"或"全错"两种结果，**不存在部分解出** |

### 2.1 关键发现一：载荷的失效是**悬崖式**的

实测载波几何：

```
carrierBits 2560 · bitsUsed 2040 (= 255 B) · codewords 1 · depth 1 · nsym 32
```

**整个载荷（215 B）只装在一个 255 字节的码字里**——载波虽能容纳 320 B，但码字长度就是 255 B，
装不下第二个。所以：

- **交织深度实际为 1**（只有一个码字可交织），这与 tech.html 的 **L4**（"交织深度受码字数限制，
  端到端实际为 1–2"）完全吻合，本轮给出了它的**实测后果**：没有交织增益，RS 一失败就**整张秘密图全灭** ✓
- 这解释了为什么 32k 与 16k 两个用例是"秘密图 ❌"而不是"秘密图质量下降" ✓

### 2.2 关键发现二：存在**两个互不相同的**失效阈值

| 阈值 | 触发用例 | 机理（实测数据） |
|---|---|---|
| **① RS 纠错预算** | `m4a 32k`：BER **1.372%**（28/2040 位） | 块均值漂移只有 **0.436**（**仅为裕度的 7.3%**），QIM 判决基本是对的；但 28 个位错散布在 **>16 个字节**上，**超过 RS(255,223) 的 16 符号纠错上限** → 码字失败 |
| **② QIM 判决裕度** | `webm 16k`：BER **40.392%**（824/2040 位） | 块均值漂移 **7.867 > Δ/2 = 6**（**131% 的裕度**）→ 判决**接近随机** → 灾变式崩塌 |

**这两个阈值性质不同**：① 是"纠错不够"（信息还在，但修不回来）；② 是"判据失效"（信息本身已被破坏）。
`webm 16k` 连公开图都掉到 **18.89 dB**，说明该码率已把信号本身破坏到不可用 ✓

### 2.3 关键发现三：损伤**高度集中在图像最前部**

存活用例的翻转位位置（载波共 2040 位）：

| 用例 | 翻转位置 |
|---|---|
| m4a | `[2, 3, 4, 6, 10, 19]` |
| mp3 192k | `[3, 5, 7, 8, 9, 10, 19]` |
| webm 128k | `[0, 2, 9, 10, 19]` |
| ogg q6 | `[2, 4, 6, 9, 10, 19]` |
| mp3 64k | `[16]` |
| ogg q0 | `[2, 4, 10, 19, 496, 532, 1150, 1152]` |

**几乎全部翻转落在 bit 0–19**，即图象的**最前 20 个承载块**——那里正是解调器刚过完标定头、
逐行同步与时序尚未收敛的位置。

**载荷帧布局是 `magic(1) | version(1) | length(2) | CRC32(4) | data`**（`js/payload-pipeline.js:9`），
所以 bits 0–19 **正是帧头**。它没坏，说明 **RS 把这几处错纠回来了** ✓——即载荷是**靠纠错码救回来的**，
不是"没受影响"。

## 3. 量化退化数据（报告第 3 项）

### 3.1 你说的"CRC 失败块数 / 总数"

| 用例 | 码字失败/总数 | 等价描述 |
|---|---|---|
| 4 种默认格式 + mp3 64k + ogg q0 + m4a×2 | **0 / 1** | 唯一码字译码成功 |
| m4a 32k、webm 16k | **1 / 1** | 唯一码字译码失败 → 秘密图全灭 |

**注意口径**：这里的"块"是 **RS 码字**，不是 QIM 承载块。承载块共 255 个（每块 1 位），
而码字只有 1 个。所以 `0/1` 与 `1/1` 是**全部信息**——粒度很粗，这本身就是 L4 的直接体现。

### 3.2 更细的退化度量

| 指标 | 存活区间 | 失败区间 | 意义 |
|---|---|---|---|
| pre-FEC BER | 0.049% – 0.392% | 1.372% / 40.392% | FEC **之前**的硬判决错误率 |
| 块均值漂移 | 0.052 – 0.306 灰阶 | 0.436 / 7.867 | QIM 失效的**机理量** |
| **漂移 / 裕度(6)** | **0.9% – 5.1%** | **7.3% / 131%** | **最好的单一预测指标** |
| 公开图 PSNR | 28.54 – 45.79 dB | 27.48 / 18.89 dB | 模拟通道本身的退化 |
| bitErasureRate | 0.29% – 1.91% | 5.29% / 36.27% | 提取器自报的不确定位比例 |

### 3.3 三条反直觉的实测结论

1. **码率不是单调的**：`mp3 64k` 的 BER（**0.049%**，全场最低）**优于** `mp3 192k`（0.343%）；
   `ogg q0`（0.392%）与 `ogg q6`（0.294%）几乎一样。→ **编码器的具体伪影比标称码率更重要** ✓
2. **二次转码不累积**：`m4a ×2` 的 9 项指标与单次 `m4a` **完全相同**（BER 0.294%、漂移 0.052）
   → 高质量 AAC 反复转发不会逐步劣化，**转发一次和转发两次没有区别** ✓
3. **公开图与载荷的鲁棒性差距极大**：`webm 16k` 下公开图仍能解出（PSNR 18.89 dB，已很差），
   而载荷彻底失败。**不能从"公开图解出来了"推断"载荷也还行"** ✓

## 4. 三条修复路线的评估（报告第 4 项）

### 路线 A：提高载荷冗余度（增大 nsym）

| 维度 | 评估 |
|---|---|
| **预期收益** | RS 纠错上限从 16 符号提到 32 符号（`nsym 64`）→ 可容忍 BER 约从 1.4% 提到 ~2.7%。**能救回 `m4a 32k`（1.372%）**，但**救不了 `webm 16k`（40%）**——后者是 QIM 判据失效，加冗余无意义 |
| **实现代价** | **几乎为零：UI 已有"纠错档位"选择器。** 这条路线**不需要写代码**，只需要在文档里给出"经有损信道传输时用更强的档位"的建议 |
| **容量代价** | `nsym 64` → k 从 223 降到 191 → 载荷 215 B → 约 **151 B**，秘密图必须更小 |
| **架构兼容性** | **完全兼容**（参数已存在，发送/接收两侧的几何推导是自动的） |
| **判断** | **推荐作为用户侧的可选手段**，但不作为默认值——它会无差别缩小秘密图，而 7/9 的用例本来就不需要 |

### 路线 B：换用更抗重采样的调制（扩展频谱 / 块间差分）

| 维度 | 评估 |
|---|---|
| **预期收益** | **实测数据不支持"块间差分能免疫"这一假设。** 差分的价值在于抵消**常量偏移**，但实测的翻转位置是**逐块随机散布**的（`ogg q0`: 2,4,10,19,**496,532,1150,1152**），说明漂移是**每块独立的随机量**，不是常量偏置。差分只能消掉前者，对这种漂移**无效** ✓ |
| | 若改用**更大的 Δ**（量化步长）以提高裕度：能显著提升鲁棒性，但代价是**图象可见失真增大**（Δ 直接决定绿通道块均值的偏移量） |
| **实现代价** | 高：新的嵌入/提取、鲁棒性重新定标、tech.html 的图表与数字**全部需要重算**、`image-codec`/`payload-pipeline` 两个阶段的测试都要改 |
| **容量代价** | 扩展频谱通常要占用更多承载位，容量进一步下降；而容量已经是本项目的硬限制（L3：载荷仅数百字节） |
| **架构兼容性** | 能挂在 `Codec.registerEmbedder` 接缝上 ✓ 但是一次**大改**，且会削弱已建立的实测基线 |
| **判断** | **不建议做。** 现有调制在**真实合理范围**内（4 种默认格式 + 低码率 mp3/ogg + 二次转码）已经够用；真正让它失效的编码（Opus 16k）同时也把公开图打到 18.89 dB——那种信道上目标已不是"保住载荷"而是"保住图" |

### 路线 C：接受"隐藏载荷需要原生 WAV"（分级的文档说明）

| 维度 | 评估 |
|---|---|
| **预期收益** | **作为"一刀切规则"已被数据否决**（7/9 通过）。但**分级说明**价值高：明确"载荷可挺过正常码率的转码，低码率激进编码会失败；公开图远比载荷鲁棒" |
| **实现代价** | **最低**：README 与 `tech.html` 的说明文字；UI 的失败提示**已经**给出可操作的补救建议（换成 B=48/64） |
| **架构兼容性** | 完全兼容，零代码改动 |
| **判断** | **推荐作为兜底**，且必须与下面的路线 D 一起写，否则说明会不准确 |

### 路线 D（**本轮数据新发现**）：不要把载荷放在图象最前的若干承载块

| 维度 | 评估 |
|---|---|
| **依据** | **7 个存活用例中，几乎全部翻转都集中在 bit 0–19**（`mp3 64k` 仅 1 处翻转，就在 bit 16）。这段区域对应解调器时序尚未收敛的图象最前部 |
| **预期收益** | 对存活用例：`m4a` 的 6 处翻转**全在 0–19**，避让后 **BER 归零**（RS 无需纠错）；对 `m4a 32k`：28 处中 6 处在 0–19，避让后仍有 22 处 > 16 符号上限，**救不回来** → **只增裕度、不移动悬崖** |
| **实现代价** | 低-中：在承载位映射上加一个"跳过前 N 块"的守卫区（发送/接收对称）。会改动 `payload-qim.js` 的位映射，需重新验证 |
| **容量代价** | 极小：跳 20 块 / 共 255 块 ≈ **约 8%** 承载位（载荷 215 B → 约 195 B） |
| **架构兼容性** | 兼容（位映射是 `PayloadQIM` 的内部细节），但**改变了载荷格式**，会使**旧音频无法被新接收端解出**，需要版本化 |
| **判断** | **技术上最划算的一条**（代价小、裕度收益直接可测），但要接受格式版本化。**建议先做一次"只改文档 + 用现有 nsym 档位"的最小动作，把路线 D 作为下一次改动的候选** |

## 6. 你的建议：下一步做哪条路线（报告第 6 项）

**建议按以下顺序，只做第一步就够**：

1. **【立即可做，零代码】路线 C 的分级说明 + 路线 A 的操作建议**
   在 README / `tech.html` 写明三句话：
   - 公开图**支持所有格式**（含手机录屏的 MP4/WebM）；
   - 隐藏载荷可挺过**正常码率**的转码（实测 4 种容器 + 64k mp3 + q0 ogg + 二次转发均成功，秘密图**逐字节一致**）；
   - **激进低码率**（实测 AAC 32k、Opus 16k）会让载荷失败，且此时**公开图也已严重劣化**；此时可改用更强的纠错档位（UI 已有）。
2. **【可选，需很小改动】路线 D**：给最前 ~20 个承载块加守卫区。代价小、收益可测，但需载荷格式版本化。
3. **【不建议】路线 B**：实测数据不支持"块间差分能免疫"的假设，且改动面过大。
4. **【不建议作为默认】把 nsym 调大**：应作为用户可选，因为它无差别缩小秘密图。

**一句话结论**：**"隐藏载荷需要原生 WAV"这个担忧不成立；真正该做的是把适用边界写清楚，而不是改调制。**

## 9. 遗留与建议

1. **本轮只测了单张载体/秘密图组合**（`page-carrier.png` + `page-secret.png`）。
   不同内容的载体（尤其是低对比度、含大面积平坦区）块均值漂移可能不同——建议后续用
   `tests/fixtures/real/` 的素材再跑一组，确认 0.9%–5.1% 的漂移区间是否具有普遍性。
2. **`nsym 64` 是否真能救回 `m4a 32k`，本轮未实测**（只做了理论推算：16→32 符号上限）。
   若你决定采用路线 A 的文档建议，建议补一次 `nsym 64` 的实测以免给用户未经验证的建议。
