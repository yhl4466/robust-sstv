## 2. 那么"扁的、接近正方形"是什么原因？

### 2.1 一个关键的算术事实

本项目支持的全部四种模式**都是横屏**：

| 模式 | 光栅 | 比例 |
|---|---|---|
| Martin M1 / Scottie S1 | 320×256 | **1.25:1（宽 > 高）** |
| PD120 / PD180 | 640×496 | **1.29:1（宽 > 高）** |

**任何正确的 SSTV 解码都不可能产出"长图"（竖图）。** 所以：

> 如果 Robot36 显示的是**竖的"长图"**，而我们的工具显示的是**横的 1.25:1**，
> 那么**我们的显示才是符合 320×256 光栅的那种**，Robot36 一定对内容做了旋转（或发送端做了旋转）。

### 2.2 最可能的真实原因：**内容方向，而非宽高比**

设想发送端是一张**竖屏照片/手机截图**（例如 9:16）。SSTV 的栅格是 1.25:1 横屏，所以发送端必须二选一：

- **旋转 90°** 后填入栅格（多数 App 的做法）→ 栅格里躺着一张侧躺的图
- **直接压缩**填入 → 内容被水平拉伸

若是前者，接收端若不把图转回来，看到的正是"**一张竖图横躺着**"——在你眼里就是**"扁的"** ✓
而 Robot36 若自动或手动转正，你看到的就是"**长图**" ✓ **这与你的描述完全吻合。**

我实测确认：**本项目的显示路径没有任何旋转能力**——`js/`、`js/lib/` 与四个页面里
`rotate` / `transpose` / `旋转` / `orientation` **零命中**（唯一的 transpose 是交织器，
其余的命中是论文 SVG 的 `text-anchor`）。所以我们是**如实显示光栅**，不做任何方向处理。

### 2.3 我无法在没有你的文件时进一步断定

以上是**最符合现象的解释**，但我**没有你的那段音频**，无法验证到底属于"旋转"还是"压缩"。
两种情况的修法完全不同：

- 若是**旋转**：需要的是**显示端的 90° 旋转选项**（或自动方向检测），**与宽高比无关**
- 若是**压缩**：那是**发送端**把竖图挤进了横栅格，任何接收端（含 Robot36）看到的都会是被拉伸的内容——
  我们能做的只是提示用户，而无法"修回来"

## 6. 顺带发现的**唯一**真实显示层缺陷（不是你说的那个）

`css/style.css:183`：

```css
canvas.thumb { width: 204px; height: 96px; image-rendering: pixelated; }
```

**该规则没有 `max-width`**，宽度被钉死在 204px。逐档计算视口可用宽度：

| 视口 | 可用内容宽（减 `.wrap` 40 + `.preview` 24） | 204px 缩略图 |
|---|---|---|
| 390px | 326px | ✓ 放得下 |
| 320px | 256px | ✓ 放得下 |
| 280px | 216px | ✓ 放得下 |
| **260px** | 196px | **✗ 溢出 → 会产生横向滚动** |
| **240px** | 176px | **✗ 溢出** |

**影响范围**：视口窄于约 260px——**比任何真实手机都窄**（最窄的常见设备约 320px），
所以这是一个**理论缺口**，不是你现在遇到的问题 ✓ 修法是把该规则补成
`max-width: 100%; height: auto;`（在正常宽度下仍渲染 204×96，比例不变）。
