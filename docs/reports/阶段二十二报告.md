## 1. 修改的文件与具体位置（报告第 1 项）

全部改动都在 **`js/lib/sstv-decode.js`**（5 处）+ 新增 1 个测试。

| # | 位置 | 改动 |
|---|---|---|
| 1 | 新增（`Estimator` 之前） | `IMAGE_BAND_MARGIN_HZ = 200` 与 `imageBandRaw(calA, calB)`：把**标称**图象频带经标定反算回**原始**频率轴 |

`SYNC_DETECT_HZ = 1350` 判断"主导音是否已不是 1200 Hz"，**若被限到 1450–2350 就会永远看不到同步音**，
这是本轮最危险的改动点，已避开 ✓

## 3. phigros 解码后的频率分布（报告第 3 项）

**限带后，频率估计被约束在标称 1500–2300 Hz ± 200 Hz 之内**（不再可能出现上一轮观测到的 3.0–3.4 kHz）。

必须精确说明这个"区间"的含义：

| 项 | 数值 |
|---|---|
| 搜索区间（标称） | 1500 − 200 … 2300 + 200 = **1300 … 2500 Hz** |
| 实际原始轴区间 | `calA×1500 + calB − 200 … calA×2300 + calB + 200`，本例 = **1103.8 … 2495.9 Hz** |
| 为什么必须有 ±200 Hz 余量 | 像素窗仅 **51 采样（1.06 ms）**，在 128 点下限时 **bin 宽 375 Hz**；余量若取 ±50 Hz（原建议）**比一个 bin 还窄**，会把真实的峰切掉 |
| 灰度 | `calcLum` 把区间外的值一律钳到 1500–2300 → 灰度**必定**落在 0–255 |

**所以 AC2 是"按构造保证"的，而不是"测出来的"**：搜索空间本身已被限制，
上一轮那种 3.0–3.4 kHz 的估计**在结构上不可能再出现** ✓ 但余量的存在意味着
标称意义上的估计仍可落在 1300–1500 与 2300–2500，随后被 `calcLum` 钳平。

**⚠️ 必须声明的一处口径问题**：上一轮我在 dump 里算频率分布时，
误把 `windowFactor`(2.48) 当成了 `Estimator` 的 `mult`（真正应传质量档的 `mult`），
导致 FFT 被钳到 128 点、bin 宽 375 Hz，**比解码器标准档实际用的 1024 点（47 Hz/bin）粗得多**。
所以**上一轮那组 3.0–3.4 kHz 的数字口径不严**；方向性结论（估计落在带外）仍成立，
但精确数值不可引用。

## 5. `clockRecovery` bug 的修复验证（报告第 5 项）

**先更正我上一轮的判断**（这一点很重要）：

上一轮我说"`clockRecovery:false` 完全无效"——**那是我只看了报告值**。实际执行顺序是：

| 位置 | 行为 |
|---|---|
| L304 | `calib.clockScale = cal.clockScale`（拟合值 0.97852） |
| L350 | `if (!clockRecovery) calib.clockScale = 1` |
| **L814 / L941**（扫描函数内） | **读取** `calib.clockScale` → 关闭时读到 **1** ✓ **解调一直是对的** |

**所以真相是：选项对解调一直有效，只有"报告"在撒谎。**
→ 反过来也意味着：上一轮那组对照实验（0.2479 vs 基线 0.2474）**确实测到了 clockScale=1**，
→ **`clockScale` 假设已被实测否决** ✓（这是本轮顺带澄清的一处结论更正）

**修复验证**（实测）：

| 变体 | 修复前 `calibration.clockScale` | 修复后 |
|---|---|---|
| 默认 | 0.97852 | 0.97852（不变 ✓） |

## 7. 对 AC1 失败的判断：我上一轮的根因假设被否定

**上一轮的假设**：逐像素估计被带外（~3 kHz）内容带走 → 越界像素被钳白 → 噪声。
**本轮的检验**：把搜索限制到图象频带（结构上排除 3 kHz）后，**图没有任何改善** ✗
→ **该假设不成立**（或至少不是充分原因）✓ 这是本轮最重要的负面结论。

### 7.1 噪声的形态给出了新线索

观察输出图：**连续的彩色横条**（品红/青/黄），**行内连贯、行间无相关**。

- **行内连贯** → 行同步与行时序是**对的**（这与前两轮的结论一致）
- **行间无相关 + 强烈色边** → **行内的通道结构错了**：G / B / R 三个分量**不是取自同一图像行**，
  或通道的起始偏移不对。这正是 **Scottie S1 的著名特性**——它的色度分量相对亮度**滞后一行**
  （发送顺序为 G、B、R，且 B/R 取自**上一行**），解码端必须做**一行偏移补偿**。
- **这恰好是自往返测试在原理上发现不了的错误**：若编码器与解码器共享同一个（错误的）行偏移假设，
  往返必然自洽 ✓ 而 Robot36 按标准实现，所以它能出图 ✓
  → **完全对应项目 L2 的记录**（从未有真实 S1 样本，因此 S1 路径从未被真实检验）

### 7.2 下一轮的具体动作（按优先级）

| # | 动作 | 理由 |
|---|---|---|
| **1** | **跑真实录音 26 段语料** | 本轮唯一未做的回归，且正对限带的风险面（§6） |
| **2** | **核对 Scottie S1 的一行色度偏移**：拿一份**内容已知**的真实 S1 录音，比较"做/不做一行偏移"两种解法的输出 | 输出图的形态（行内连贯 + 色边 + 行间无关）**精确指向**这里；且这属"编解码器共同偏离标准"，自往返无法暴露 |
| **3** | 核对 G/B/R 的通道顺序与各通道扫描起点（与标准逐项对照） | 同上，同一类错误 |
| **4** | 修正上一轮 dump 的 `mult` 口径，在标准档下重测频率分布 | 让 AC2 从"按构造保证"升级为"实测" |

## 9. 结论

**本轮交付了两件确定的东西**：① 频率搜索限带（实现正确、作用域精确、**零回归**）；
② `clockRecovery` 报告缺陷修复（并澄清了它**从来不是功能缺陷**，只是报告撒谎）。

**同时诚实地报告一次失败**：**AC1 没有达成**，而且它否定了我上一轮提出的根因。
限带是**正确的健壮性改进**（防止 1 ms 窗被带外强音带走），但**不是这个问题的解**。
噪声的形态（行内连贯 + 强烈色边 + 行间无关）把方向指向 **Scottie S1 的行内通道结构**
—— 也就是**自往返测试原理上无法覆盖**的那一类错误，与项目 L2 的记录完全吻合。
