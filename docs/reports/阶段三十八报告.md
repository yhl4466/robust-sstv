## 1. 测量方法

`tests/diagnose-chroma-pixels.js`，用**阶段三十七修好的暴力 DFT 探针**逐像素测量：

| 量 | 定义 |
|---|---|
| `σ(G−R)`、`σ(G−B)` | 色差图的标准差（灰阶） |
| `σ(L)` | 亮度标准差 |
| **`σ(G−R)/σ(L)`** | **色度相对幅度**（比较的关键量） |
| **G−R 行间自相关** | **结构化色度**：内容的色差在相邻行相关，噪声不相关 ✓ |

## 2. 三方色度对照表（报告第 1、2 项）

### 2.1 幅度

```
  来源            σ(G−R)  σ(G−B)   σ(L)    σ(G−R)/σ(L)  σ(G−B)/σ(L)  亮度均值
  合成 S1（真值）    2.3     2.6    73.9       0.0314       0.0356     127.2
  phigros         94.6    47.6    65.3       1.4497       0.7300     150.9
  Robot36 参照     60.5    55.1    76.1       0.7952       0.7242      90.0
```

### 2.2 ★ 第一行是整张表的校准基准

**合成 S1 是灰度斜坡（R=G=B）→ `σ(G−R)` 必须 ≈ 0** ✓
**实测 2.3 灰阶** ✓✓ → **探针管线没有系统性地伪造色度** ✓
（若管线本身会造出假色度，这一行不会是 2.3 ✓）**这是本轮结论可信的前提** ✓

### 2.3 第二、三行的判读

| 观察 | 含义 |
|---|---|
| **phigros `σ(G−R) = 94.6`** ✗ | **色差幅度很大 —— 不是"没色"** ✓ |
| **比参照（60.5）高 56%** ✗ | **而且注意参照是降采样过的截图**（降采样必然压低 σ）✗ → **真实差距更大** ✓ |
| **`σ(G−R)/σ(L) = 1.4497`** ✗ | **色度变化超过亮度变化** ✗ —— 正常图像里色度幅度应小于亮度 ✓ |
| **phigros 亮度均值 150.9 vs 参照 90.0** ✗ | **我们明显偏亮** ✓（与"整体发灰白"的观感一致 ✓）|

### 2.4 结构（AC2）

```
  来源            G−R 行间相关   G−B 行间相关
  合成 S1（真值）      0.9049         0.9212     ← 但 σ(G−R)=2.3，近零信号上的相关无意义 ✗
  phigros            0.5398         0.3347
  Robot36 参照        0.2281         0.4147
```

**⚠️ 这个指标本轮未能区分好坏** ✗：
- **合成 S1 的 0.90 是在 2.3 灰阶的近零信号上算的** ✗ **无参考价值** ✓
- **phigros（0.54）高于参照（0.23）** ✗ —— 但**行相干的噪声也会产生高行间相关** ✓
- → **行间自相关不足以区分"内容色度"与"行条带色度"** ✗ **需要列方向（行内）的结构指标** ✓（下一轮）

**这是本轮的一处方法论缺口，如实记录** ✓

## 3. 四种窗长对比（报告第 3 项）

```
  窗长(像素)  实际采样   σ(G−R)  σ(L)    σ(G−R)/σ(L)  G−R 行间相关
        1.00         21    163.4   69.0       2.3678        0.0171   ← 比率最高但相关塌了 ✗
        1.50         31    104.2   62.6       1.6642        0.3389
        2.00         41     97.2   63.2       1.5384        0.3967
        2.48         51     95.6   65.1       1.4689        0.4219   ← 当前
        3.50         73     95.3   66.7       1.4283        0.4328
```

### 3.1 ★ 若只看比率会得出错误结论

**1.0 像素窗的 `σ(G−R)/σ(L) = 2.3678` 比当前高 61%** ✗
**但它的 `G−R 行间相关 = 0.0171`** ✗✗ —— **色差图与下一行完全无关 = 纯噪声** ✓
→ **缩短窗长不是"恢复色度"，而是"增加噪声"** ✓✓ **这是一个必须靠第二个指标才能避开的陷阱** ✓

### 3.2 结论：**窗长不是原因**

- **1.5–3.5 像素区间内**，比率在 1.43–1.66 之间**基本平坦** ✓ 无明显最优 ✓
- **当前 2.48 像素在行间相关上接近最好（0.4219 vs 3.50 的 0.4328）** ✓ **是合理折衷** ✓
- → **AC3 判定：窗长不是"没色"的原因** ✓

## 4. "没色"根因（报告第 4 项）

### 4.1 三条排除

| 候选 | 判定 |
|---|---|
| ① 逐像素色度幅度低（AAC + OBS 低通） | **排除** ✗ `σ(G−R) = 94.6` **高于参照** ✓ |
| ② 解码器窗长过长 | **排除** ✗ §3：缩短只增加噪声 ✓ |
| ③ 我们的映射压缩色度 | **排除** ✗ 合成 S1 上映射正确（`σ(G−R)=2.3`）✓ |

### 4.2 ★ 更新后的准确表述

**"没色"的准确表述是：颜色量很大，但结构是错的 —— 表现为行的条带而非图像内容** ✓

**证据链**：
- **色差幅度大**（94.6 > 参照 60.5）✗
- **但色度/亮度比异常**（1.45；正常应 < 1）✗
- **且亮度均值偏高**（150.9 vs 90.0）✗
- **与视觉症状吻合**：你截图里的**品红/青横条纹**正是"行相干的色差条带" ✓
- **而"糊"来自亮度通道**（行间相关 0.61，尚未达到成图质量 0.8+）✓

**→ 因此问题不在"色度有没有"，而在"三个色平面的逐像素对应关系"** ✓
**最可能的机制**：**三个槽各自采到了正确频段，但 G/B/R 之间的时间/相位对应不对**
（例如某一通道整体偏移若干像素，或逐像素估计在通道内不一致）✗
**这与"行条带"的症状一致**：通道内的一致性让条带沿行方向连贯 ✓

### 4.3 下一轮的直接验证手段

**列方向（行内）结构指标** ✓：
- 计算色差图 `G−R` 的**行内自相关**（沿 x 方向，lag 1..8）
- **内容色度**在行内**空间相关**（相邻像素相关）✓
- **逐像素估计噪声**在行内**不相关** ✓
→ **这次能区分"行条带色度"与"内容色度"** ✓（补上 §2.4 的缺口）

## 5. 标定质量门实现（报告第 5 项）

### 5.1 改动位置：`js/lib/sstv-decode.js` L361 起（原 L361-364）

**改动前**（`afcMode === 'affine'`，即默认）：
```js
} else if (cal) {
  calib.a = cal.scale;        // ← 唯一来源：同步拟合，无任何质量检查 ✗
  calib.b = cal.offsetHz;
  calib.source = 'sync-calibration';
}
```

**改动后**：
```js
var nomLine = Modes.lineTime(mode) * sampleRate;
var resRms = cal.residualRmsSamples;
var gateSamples = nomLine * 0.05;                  // ≈1028 采样
var syncFitGood = isFinite(resRms) && resRms <= gateSamples;
calib.syncFitResidualRms = resRms;
calib.syncFitGateSamples = gateSamples;
calib.syncFitAccepted = syncFitGood;
if (syncFitGood) {
  calib.a = cal.scale;  calib.b = cal.offsetHz;  calib.source = 'sync-calibration';
} else if (hdr.a && isFinite(hdr.a) && hdr.a > 0) {
  calib.a = hdr.a;      calib.b = hdr.b;         calib.source = 'sync-rejected-header-fallback';
} else {
  calib.a = 1;          calib.b = hdr.leaderFreq ? (hdr.leaderFreq - 1900) : 0;
  calib.source = 'sync-rejected-leader-offset';
}
```

**三级回退**：同步拟合 → **标定头拟合** → **不缩放 + 前导锚定偏置** ✓
（`nomLine` 在本地重算 —— 标定段之后的 `var nominalLineSamples` 虽被提升但此时尚未赋值 ✗）

**并把 `syncFitGateSamples` / `syncFitAccepted` 加入 `calibration` 白名单** ✓

### 5.2 验证（AC6/AC7）

```
合成 S1 : source=sync-calibration                accepted=true    残差=4.9      门限=1028  scale=1.000000  行间相关=0.9987
phigros : source=sync-rejected-header-fallback   accepted=false   残差=20822.7  门限=1028  scale=0.989806  行间相关=0.6126
```

| 语料 | 行为 | 判定 |
|---|---|---|
| **合成 S1** | 残差 **4.9** ≪ 1028 → **接受同步标定**，`scale = 1.000000` ✓ | **AC7 ✓**（且行间相关 0.9987 不变 ✓）|
| **phigros** | 残差 **20822.7** > 1028 → **拒绝，回退标定头**，`scale = 0.989806`（= `hdr.a`）✓ | **AC6 ✓** |

**并且 phigros 的行间相关从 0.6096 提升到 0.6126** ✓（幅度小但方向正确 ✓）
