## 2. 偏差模式分析（报告第 2 项）

### 2.1 决定性的对比

| 量 | 对照组（我们自己，可解） | phigros（真实录音，噪声） | 差异 |
|---|---|---|---|
| **到最近真值同步的距离（中位）** | **99 采样（4.8 像素）** | **5926 采样（286 像素）** | **60 倍** ✗ |
| 该距离的最大值 | 133 采样 | **13770 采样（≈ 半行）** | 100 倍 ✗ |
| Δ 抖动（MAD） | 12 采样（0.58 像素） | 5944 采样（287 像素） | 500 倍 ✗ |
| Δ 漂移（R²） | 0.0011（无） | 0.0018（无） | 都无漂移 |

**结论：在能解出的音频上，解码器的逐行参考牢牢咬住真值同步脉冲（差 4.8 像素）；
在 phigros 上它落在离任何真值同步都很远的地方（中位 286 像素，最远达半行）。**
→ **解码器的逐行同步锁定在真实录音上没有锁到真正的同步脉冲** ✓ **与"行首定位/同步锁定"假设方向一致** ✓

### 2.2 一条很强的定量线索

phigros 前 14 行的 Δ 稳定在 **−6992 .. −8666 采样**。这个量级对应的是：

```
syncPulse + sepPulse + scanTime = 9 + 1.5 + 138.24 = 148.74 ms = 7139 采样
```

**即 `chanTime + syncPulse` —— 恰好是 L649 / L868 那个"回绕"的量** ✓
也就是说：在真实录音上，解码器的参考**恰好落在真值同步之前约一个回绕量**处 ✗
这条线索与"回绕公式在真实录音上不成立"直接吻合 ✓

### 2.3 ⚠️ 必须声明的一处数据不可靠

**Δ 的中位数（−333）不可信**，理由：
- §1.2 的逐行 Δ 明明都在 −7000 附近，中位数却是 −333，**自相矛盾** ✗
- 极值是 −13770 .. +10260 → **正负两侧都有**，说明最近邻配对在部分行**翻到了另一侧的脉冲**
- 原因：我的 phigros 真值脉冲流**被音乐产生的假脉冲污染** —— 检出 **557** 个，而
  220 s ÷ 428 ms ≈ **514** 个 → **多出约 43 个假脉冲** ✓ 这些假脉冲散布在真脉冲之间，
  会抢走部分行的"最近邻" ✓
- 因此 **Δ 统计与"MAD 287 像素"这个判定数字不可直接引用**；
  可靠的只有 **"到最近真值同步的距离中位 5926 采样"** 这一类**与配对无关**的量 ✓

**修正方法（下一轮第一步）**：先对真值脉冲流做**规整性筛选**（例如 RANSAC 拟合 428.00 ms 栅格，
只保留落在栅格 ±2 ms 内的脉冲），把假脉冲剔掉，再重做配对 ✓

## 3. sepPulse 一致性核查结论（报告第 3 项）

### 3.1 四层核查

| 层 | 结果 |
|---|---|
| **① 编码器实际发了什么** | `sstv-timeline.js:130-140` 的 scottie 分支：<br>`segs.push(tone(FREQ_SYNC, syncPulse))`（L131 前导同步）<br>`for ci: if (ci===chanSync) push(sync); push(tone(FREQ_PORCH, sepPulse)); push(scan)`（L135-137）<br>→ **发射顺序 `[SYNC][sep][G][sep][B][SYNC][sep][R]`，分隔脉冲确实存在** ✓ |
| **② 解码器假定什么** | `chanTime = mode.sepPulse + mode.scanTime`（L782）→ **假定通道间有分隔** ✓ |
| **③ phigros 有没有** | **有**：5633 个 1500 Hz 短脉冲，宽度中位 **1.00 ms**（标准 1.50 ms），**97.7%** 与某个同步脉冲同线 ✓ |
| **④ 我们自己的音频** | **也有**：642 个，宽度 1.00 ms，同线比例 **100%** ✓ |

### 3.2 结论：**情况 C 排除**，并且**我上一轮的说法是错的**

编码器**确实**发分隔脉冲、解码器**也**确实假定有、phigros **也**确实有 →
**三边一致，sepPulse 不是根因** ✓

> **更正记录**：我在阶段二十二报告里写过「`sstv-timeline.js` 的 scottie 分支只发 sync 与 scan，
> 不发 `sepPulse`」。**这是错的** —— 当时只看了片段，`segs.push(tone(FREQ_PORCH, mode.sepPulse))`
> 就在 L136，`ci===chanSync` 的判断在 L135。这是本系列**第四次**因只读片段而误判，
> 也是本轮坚持"先实测再下结论"的又一次理由。

**顺带一个可疑点**：分隔脉冲实测宽度中位 **1.00 ms**，而标准 `sepPulse = 1.5 ms`。
两者**都**是 1.00 ms（对照组也是），说明这是**我的检测器**在 2 ms 一阶包络下的固有压缩，
不是音频的问题 ✓ 记录在此以免被误读为"音频的分隔偏短"。

## 6. 本轮我自己犯的三个错（全部已修正，且都曾把结论带偏）

| # | 错误 | 后果 | 修正 |
|---|---|---|---|
| 1 | **sepPulse 说法错**（阶段二十二） | 误导了一整轮的方向 | 本轮读全 `sstv-timeline.js:130-140` 并**实测**两侧音频 ✓ |
| 2 | **同步检测阈值依赖内容**（`eRef=(e19+e23)/2`） | 对照组图象是灰度斜坡、左端内容是 1500 Hz，导致 e19/e23 很低 → **误检出 588 个"同步"、间隔中位 152 ms** ✗ | 改为"**目标音必须是局部最强音**"（`e12 > k·max(e15,e19,e23)`）→ 对照组变成 257 个、MAD **0.000 ms** ✓ |
| 3 | **配对只在前 40 个真值里找最近邻** | phigros 解码器锁在 107 s（真值索引约 250）→ 全部 Δ 继承 **94 秒**的常数偏移 ✗ | 改为**逐行独立最近邻** ✓ |
| 4 | **判定阈值不容忍小恒定偏移** | 把对照组（−4.77 像素、抖动 0.58 像素）误判为"未对应候选" ✗ | 改为按**抖动与漂移**判定（逐行重锁的解码器不怕小恒定偏移）✓ |
