## 1. 最终定位的根因

`js/lib/sstv-decode.js` 的 `alignSync` 粗搜：

```js
var cs = alignStart;
for (; cs < alignStop; cs++) {
  if (f(est.peak(samples, cs, syncWindow)) > SYNC_DETECT_HZ) break;
}
```

**它从预测位置向前推进，直到"主导音不再是同步音"就停** ✗
**却从不检查起点 `alignStart` 本身是否在同步脉冲内** ✗✗

**→ 若预测位置（回绕后的 `seqStart`）落在图象内容里（>1350 Hz），循环在【第一次迭代】就 break** ✓
**→ 于是"锁定"位置就等于预测位置本身** ✓✓

**与阶段四十五的量化完全吻合**：
| | 对照组合成 | phigros（修复前）|
|---|---|---|
| 到最近真值同步 | 中位 200 采样 | **中位 7155 采样（345 px）** ✗ |
| 带符号偏差 | −200（MAD 18）| **−7149（MAD 92）** ✗ |
| 行间隔 MAD | **0.0000 ms** | **1.8750 ms（4.3 px）** ✗ |
| 偏差量级 | — | **148.96 ms ≈ `base+chanTime` = 148.74 ms**（回绕量）✓ |

**症状链**：预测位置被当成同步 → 每行内容整体偏 ~1.1 个通道长度，且各行偏移不一致 →
**模糊（4.3 px 逐行抖动）+ 行相干色度条带（各行偏移不同，三通道共用同一行参考）** ✓

## 2. 修复方案与结果

### 2.1 尝试的实现

把"向前推进"改为"**在预测位置 ±0.4 行周期内扫描，取主导频率最低者**" ✓
（理由：1200 Hz 是 SSTV 中最低的音；分隔音 1500 与图象带 1500–2300 都会被排除 ✓；
 找不到则 `return null` → 进入阶段二十九的自由运行路径 ✓）

### 2.2 ★ 量化结果：**真实录音上全部达标，且三个指标对齐参照**

### 2.4 ✗ 但它破坏了合成往返，且慢 10 倍

```
M1 photo round trip  17.27 dB   ← 从 31.23 崩落 ✗✗
S1 photo round trip  15.28 dB   ← 从 30.50 崩落 ✗✗
耗时: M1 104.8 s（原 ~10 s）· S1 138.5 s（原 ~14 s）✗ 慢约 10 倍
```

**失败原因**：**选择判据是"频率最低者胜"** ✗
在低信噪比或图象带边缘，`est.peak` 会**偶发**报出低于 1350 Hz 的值 ✓
而"更低者胜"就**必然选中那个噪声** ✓✓
**→ 该判据在真实录音（同步清晰、内容多样）上工作，在合成上（某些区域低信噪）反而中毒** ✗

**慢 10 倍的原因**：±0.4 行周期 = ±8222 采样、步长 24 采样 → 每次 `alignSync` 约 **685 次 FFT** ✗ × 256 行 × 两遍（逐行 + 标定前导）✗

### 5.2 ★ 下一轮的具体设计（已写入代码注释）

| # | 改进 | 理由 |
|---|---|---|
| **1** ★ | **用 `refineSync` 的匹配置信度给候选打分，取【最好】的**，而不是取"频率最低" ✗ | 本次失败的直接原因 ✓ 真实录音上同步清晰、合成上某些区域低信噪，"最低频率"在后者必然中毒 ✓ |
| **2** ★ | **扫描窗收窄到 ±0.15 行周期**，步长放大到 2 ms | 预测通常很近 ✓ 只有真实录音的退化段才远 ✗ 同时解决 10 倍慢的问题 ✓ |
| **3** | **两级**：粗扫（频率 < 1350 的候选）→ 逐个 `refineSync` → 取置信度最高 | 粗扫只做筛选、不做决定 ✓ |
| **4** | **用合成往返作为该改动的门禁**：任何 `alignSync` 改动**必须先跑 `roundtrip.js`** | 本次正是靠它抓住了回归 ✓✓ |
| **5** | 加一个**真实录音的最小验收**：偏离真同步 < 300 采样 + 色度比 < 1.0 | 防止"修好真实录音但悄悄改坏合成"再次发生 ✓ |
