# 阶段一报告：鲁棒 SSTV 解码网页应用

**范围**：纯前端 MVP —— 图片 ⇄ SSTV 音频的完整编解码 + 阶段二扩展接口。
**交付目录**：`robust-sstv/`（双击 `index.html` 即可运行）
**验收状态**：AC1–AC5 全部通过，且**逐条有可复现的实测证据**（见第 6 节）。

## 1. 调研并最终选择的 JS SSTV 库？为什么？

### 1.1 核心结论：不存在能双向闭环的单一 JS 库

我把所有候选的**源码实际下载下来核对**（不是只看 README），结论是必须组合使用。

| 项目 | 编码 | 解码 | 许可证 | 浏览器可用 | 最终决定 |
|---|---|---|---|---|---|
| [CKegel/Web-SSTV](https://github.com/CKegel/Web-SSTV) | ✅ M1/M2/S1/S2/SDX/WraaseSC2180/PD50-290 | ❌ **空壳** | MIT | ✅ | **编码逻辑采用** |
| [samccone/sstv](https://github.com/samccone/sstv) `sstv@1.0.0` | ⚠️ 仅 Martin 1 | ✅ M1/M2/S1/S2/SDX/R36/R72 | MIT | ❌ 需移植 | **解调核心采用** |
| [vignedev/node-sstv](https://github.com/vignedev/node-sstv) | ✅ 7 类模式 | ❌ | MIT | ❌ 需移植 | 仅作架构参考 |
| [MadjikDotPng/Better-WSSTV](https://github.com/MadjikDotPng/Better-WSSTV) | 同 CKegel | ❌ 同一空壳 | MIT | ✅ | 不采用 |
| [RussPalms/Web-SSTV_dev](https://github.com/RussPalms/Web-SSTV_dev) | 更旧版本 | ❌ 同一空壳 | MIT | ✅ | 不采用 |
| [boybook/rasterwave-node](https://github.com/boybook/rasterwave-node) | ✅ | ✅ | MIT | ❌ 原生 N-API | 不可用 |
| `sstv@0.0.1`（HerrZatacke） | ? | ? | MIT | ? | 仓库已 404 |
| `sstv-encoder`（wheresrofl） | ? | ❌ | MIT | ? | 描述即"sily project" |

### 1.2 最重要的调研发现：Web-SSTV 的解码器是**未实现的空壳**

这是必须如实报告的一点，它直接决定了本项目的架构。`sstv-decoder.js` 全文 35 行，
`process()` 内**只有注释，没有任何实现**，直接 `return true`：

```js
process(inputs, outputs, parameters){
    //Apply the Goertzel algorithm ... to idenify the VIS Header, but use FFT (for now)
    //Detect a mode and load appropriate parameters
    return true;   // ← 什么也没做
}
```

其 `decode.html` 自己就写着：*"SSTV decoding is currently under development and not currently operational."*

我进一步核对了**全部 4 个 fork**（CKegel、MadjikDotPng、RussPalms、MTkhai）：
`sstv-decoder.js` 的 git blob sha **完全一致**（`99f0b707…`，1273 字节）。**没有任何 fork 实现了解码。**

> 因此「用 Web-SSTV 完成图片→音频→图片闭环」是不成立的。编码可以用它，解码必须另找方案。

### 1.3 为什么最终是「Web-SSTV 编码 + samccone 解调」组合

**选 Web-SSTV 做编码**：唯一浏览器原生（纯 JS + Web Audio，零 Node 依赖）；模式覆盖最全
（含本阶段要求的 M1 / S1 / **PD 120**）；代码可读（`Format` 基类 + 每模式子类，模式参数以数据形式声明，易于抽取）。

**不选它做解码**：如上，解码不存在。

**选 samccone/sstv 做解调**：它是**唯一**真正实现了 SSTV 解码的 JS 库，且实现质量高
（FFT + Hann 窗 + 重心法峰值插值、标定头搜索、VIS 偶校验、逐行同步对齐、GBR/YUV 还原）。
我**实跑通了两个独立测试用例**（其自带 8 kHz 样例，以及自编码的 115 秒 Martin M1）。
但它有三个必须处理的问题：Node 专有（`pngjs`/`fs`）、**不支持 PD 系列**、**性能极差**（实测 112 秒/张）。

**编码为何不选它的编码器**：只支持 Martin 1，不满足模式要求。
**PD 120 解码**：无任何 JS 库支持 → **本阶段范围外**（已与您确认），编码支持，解码时返回明确错误。

### 1.4 顺带发现的第三方缺陷（均已在本项目中修正或规避）

| 缺陷 | 位置 | 说明 |
|---|---|---|
| **Scottie S1 的 VIS 码错误** | Web-SSTV `encode.js` | 其数组 `[0,0,1,1,1,1,0]` 求值为 VIS **30**，而标准 S1 是 **60**。其 M1/M2/S2/SDX/PD50/90/120/180/240/290 全部正确，**仅 S1 与 PD160 有误**。若直接照搬，S1 将无法被任何标准解码器识别。 |
| **VIS 码二次反转** | Web-SSTV `encode.js` | `encodeHeader()` 用 `VISCode.reverse()`（**原地修改**），而播放与下载共用同一 `Format` 实例 → 第二次编码 VIS 变回 MSB 序，解码端失败。 |
| **PD 时长高估 2 倍** | Web-SSTV `encode.js` | `getEncodedLength()` 按 `numScanLines` 计数，实际循环是 `scanLine += 2`。PD120 算出 252.2 s、实际 126.1 s → 下载的 WAV 后一半是静音，渲染时间翻倍。 |
| **PD 的 Y 映射丢对比度** | Web-SSTV `encode.js` | 其 Y 项带 `+6` 偏移，白色只到约 2206 Hz（而非 2300 Hz）。 |
| **`RobotBW8` 引用未定义类** | Web-SSTV `encode.js:615` | 死代码（下拉框无此选项），不收录。 |
| **S1 解调质量差（~18 dB）** | samccone/sstv | 无测试（`"test": "exit 1"`）、其编码器不能产生 S1，故 S1 解码路径从未被作者验证过。 |
| **分析窗未对准像素中心** | samccone/sstv | 窗口中心对齐到像素**前沿**而非中心（少了 `+0.5`），恰好被其同步启发式约半像素的偏差掩盖。 |
| **边界判断 `>=` 差一** | samccone/sstv | `px_end >= length` 使信号末尾与最后一个像素齐平时被误判为截断。 |

## 2. 库的 API 概览与核心调用代码

### 2.1 Web-SSTV 编码器（原始形态：全局作用域 + DOM 耦合）

它**不是模块**，没有 `export`，顶层直接 `document.getElementById()` 并把 `onclick` 挂在按钮上。
可用的只有这些类：

```js
const fmt = new PD120();                 // 或 new MartinMOne() / new ScottieOne() ...
fmt.prepareImage(imageData.data);        // 入参 canvas 的 RGBA Uint8ClampedArray
const endTime = fmt.encodeSSTV(oscillator, startTime);  // 把频率曲线排程到 AudioParam，返回结束时刻
fmt.getEncodedLength();                  // 预估时长（⚠️ PD 家族有 2× 高估 bug）
```

关键点：它并不自己算样本，而是用
`oscillator.frequency.setValueCurveAtTime(curveArray, time, duration)`
把每个扫描段的频率曲线交给浏览器音频线程合成。

**本项目为何要重构它**：这个设计对阶段一够用，但**无法在样本级写入**——而阶段二的 LDPC/隐写恰恰需要。
因此我保留其**模式时序定义**（核对无误的部分），把合成改为自研的样本域实现（见第 4、5 节）。

### 2.2 samccone/sstv 解码器（Node 形态）

```js
import { readWav, SSTVDecoder } from 'sstv';
const { samples, sampleRate } = await readWav('input.wav');
const decoder = new SSTVDecoder(samples, sampleRate);
const png = decoder.decode(skipSeconds);   // 失败返回 null
```

内部四阶段（移植时完整保留）：

| 方法 | 作用 |
|---|---|
| `_find_header()` | 以 2 ms 步长扫描标定头：1900 → 1200(break) → 1900 → 1200(VIS start)，判定容差 ±50 Hz |
| `_decode_vis()` | 读 8 bit（7 数据 + 1 偶校验），LSB 优先，查 `VIS_MAP` |
| `_decode_image_data()` | 逐行对齐 1200 Hz 同步头，逐像素取窗 FFT 峰值 → `calc_lum(freq) = (f-1500)/3.1372549` |
| `_draw_image()` | 按 `COL_FMT.GBR/YUV/RGB` 还原 RGB |

### 2.3 本项目对外 API（阶段一交付形态）

```js
// 编码：图片 → 样本 → WAV 字节
const fitted = SSTVEncoder.fitToMode(imgElement, mode);     // 等比缩放居中到模式栅格
const res    = SSTVEncoder.encode(fitted.imageData, 'M1');   // → { samples, sampleRate, duration, timeline, capacity }
const wav    = SSTVEncoder.toWavBytes(res.samples, res.sampleRate);
URL.createObjectURL(new Blob([wav], { type: 'audio/wav' })); // 播放 + 下载共用同一份字节

// 解码：WAV → 图片
const parsed = SSTVDecoder.parseWav(await Decoder.readFileBuffer(file)); // 用文件原生采样率
const out    = await SSTVDecoder.decode(parsed.samples, parsed.sampleRate, {
  quality: 'standard',            // 快速 ×8 / 标准 ×16 / 精细 ×32
  wantConfidence: true,           // 输出每像素置信度（阶段二软判决用）
  onProgress: (f, label) => {},   // 分块进度
  shouldCancel: () => false       // 可取消
});
// out = { ok, imageData, mode, vis, confidence, warnings, timings }
```

页面中实际调用（`js/app.js`）：编码与播放/下载共用同一份样本，避免"听到的与下载的不一致"。

## 3. `file://` 协议下的坑（**全部为 headless Edge 实测**，非经验之谈）

| 能力 | 实测结果 | 对本项目的影响与应对 |
|---|---|---|
| `<script type="module">` | ❌ **被拦截**（触发 `onerror`） | **决定性**：`app.js`/`encoder.js`/`decoder.js` **不能用 `import/export`**。改用传统 `<script>` + `window` 命名空间，加载顺序写死在 `index.html` 中。 |
| 动态 `import()` | ❌ `TypeError` | 不能按需加载 |
| `new Worker()` | ❌ `SecurityError: Script at 'file://…' cannot be accessed from origin 'null'` | **无法用 Worker 卸载解码计算** → 只能主线程分块 + 让出（`requestAnimationFrame`）。这也是 PD120 解码无法做到秒级的根因。 |
| `audioWorklet.addModule()` | ❌ `AbortError: … cross-origin script failed to load` | 实时 AudioWorklet 解码方案在 `file://` 下**不可行**——这也解释了为何 Web-SSTV 的解码器难产。 |
| `fetch()` 本地文件 | ❌ `TypeError: Failed to fetch` | 输入只能走 `<input type="file">` + `FileReader` / `File.arrayBuffer()` |
| `OfflineAudioContext` 渲染 | ✅ 可用 | 离线渲渲染路径可行（本项目实际改为自算样本，见第 5 节） |
| `AudioContext` | ✅ 可用，初始 `state=suspended`，`sampleRate=48000` | 必须在用户点击手势内 `resume()`/`play()`，否则自动播放被拦 |
| `isSecureContext` | ✅ `true` | 好于预期 |
| `canvas.getImageData()`（画 `<img src="本地路径">` 后） | ❌ **`SecurityError` 画布被污染** | **必须**用 FileReader → `data:image/png;base64,…` 载图 |
| `canvas.getImageData()`（画 **data URL** 图片后） | ✅ **可读** | 上传图片路径确认可行 → AC2 成立 |

### 3.1 另外两条 Web Audio 的坑（与协议无关但必须处理）

**① 不要用 `decodeAudioData()` 解码 SSTV 音频。**
它会把音频**重采样**到 AudioContext 的设备采样率（并可能归一化），而 SSTV 解调的全部时序都是
按**文件原生采样率**以秒为单位计算的。真实 SSTV 录音常见 8000 / 11025 / 48000 Hz
（我实测的官方样例就是 **8000 Hz mono 16-bit**）。重采样会静默破坏每一个时序计算。
→ 本项目自写 `js/lib/wav.js`：支持 PCM 8/16/24/32-bit 与 32-bit float、单/多声道混音、
未知块跳过、`WAVE_FORMAT_EXTENSIBLE`。
→ 播放则用 `<audio src=BlobURL>` 或 `ctx.createBuffer(1, n, fileRate)`，由浏览器自行重采样。

**② `AudioContext` 建议懒创建**，并在首次点击时 `resume()`；`OfflineAudioContext` 不受自动播放策略限制。

## 4. 为下一阶段（LDPC + 图片隐藏）预留了哪些接口？

### 4.1 最关键的架构决策：走**样本域**，不走 `OscillatorNode` 排程

Web-SSTV 用 `setValueCurveAtTime()` 把合成交给音频线程，快但**无法控制单个样本**。
阶段二的隐写与 LDPC 必须在样本级写入。因此我把管线**分层**，中间留出信道层：

```
ImageData ──[sstv-timeline]──► 频率时间线 segments[{t0,t1,freq[]}]
                                     │
                       Codec.applyEmbed()   ← ★ 阶段二接缝（阶段一为恒等直通）
                                     │
                       [sstv-synth] ──► Float32 样本
                                     │
                       Codec.applyExtract() ← ★ 阶段二接缝
                                     │
                              wav.encode ──► WAV 字节
```

**关键**：这些接缝**不是文档里的设想，而是每次编解码都真的被调用**（`js/lib/sstv-channel.js`）。
接口腐烂不了，因为它们在信号路径上。页面底部的「阶段二扩展接口自检」面板会显示它们的实时状态。

### 4.2 具体接口（`js/lib/sstv-channel.js`）

```js
SSTVChannel.Codec.registerEmbedder(id, {
  capacity(meta) -> bits,                       // 该模式可嵌容量
  embed(samples, bits, meta) -> { samples, meta },
  extract(samples, meta) -> { bits, confidence }
});
SSTVChannel.Codec.registerFEC(id, { encode(bits), decode(llr) });   // LDPC（阶段二注册）
SSTVChannel.Codec.capacity(timeline) -> 各载体的解析容量估算
SSTVChannel.Channel = { awgn(samples,snrDb,seed), gain, freqOffset } // 抗干扰测试床（确定性 seed）
SSTVChannel.Metrics = { psnr, ber }
SSTVChannel.Backend  = { mode: 'local' | 'remote', setMode, encode, decode }  // ★ 双模式切换点
```

`awgn` / `gain` / `freqOffset` 已实现并可用（确定性随机种子，便于回归）。
窄带干扰、脉冲猝发等更强的干扰模型**故意留空**而不是做假的桩——那是阶段二的正题。

### 4.3 解调器输出**软判决**（接 LDPC 的必要前提）

上游实现只输出硬判决（每像素一个亮度值）。本项目的解调器可通过 `wantConfidence: true`
额外输出**每像素置信度**（峰值功率与"非邻近最佳 bin"功率之比，dB），
即 LDPC 译码所需的软信息（LLR 的原料）。

### 4.4 隐写容量估算（阶段一为**解析估算**，非已实现的信道）

实测自运行页面（阶段一未实现任何嵌入，`identity` 嵌入器容量为 0）：

| 模式 | 像素槽位 | 亮度QIM 1bit | 亮度QIM 2bit | 色度QIM 1bit | 消隐段符号 | 同步段符号 |
|---|---|---|---|---|---|---|
| Martin M1 | 245,760 | 245,760 bit | 491,520 bit | 245,760 bit | 68 | 124 |
| Scottie S1 | 245,760 | 245,760 bit | 491,520 bit | 245,760 bit | 125 | 231 |
| PD 120 | 634,880 | 634,880 bit | 1,269,760 bit | 317,440 bit | 61 | 495 |

数字来自模式结构的解析（每像素 1 或 2 bit、色度在 PD 中跨行共享故减半、
消隐/同步段按 10 ms 一个 FSK 符号粗估）。**它们是"有多少信号结构可承载"，不是"已经能可靠传多少"**
——后者必须等阶段二把 LDPC 接上并实测误码率后才能给出。

## 5. 若后续要自主实现 SSTV 核心模块，改造思路

现实是：**我们已经不得不自主实现了相当一部分**（样本合成器、PD 模式定义、解调优化）。
把这条路径完整化如下：

| 步骤 | 内容 | 本项目现状 |
|---|---|---|
| ① 模式与时序**数据化** | 把行数/像素/消隐/行长/同步头/VIS/色彩空间/行结构抽成纯数据表，与逻辑解耦 | ✅ 已完成（`sstv-modes.js`，并用两套独立实现交叉核对过时序） |
| ② 自研**样本域合成器** | 频率时间线 → 相位连续积分的样本（`phase += 2πf/fs`，段间不重置相位以避免爆音）；采样点由累计精确时间导出，避免逐段取整造成时序漂移 | ✅ 已完成（`sstv-synth.js`）。这也是阶段二的必要前提。 |
| ③ 自研**解调核** | 按窗口长度选取 `nextPow2(len×mult)` 的 FFT（而非固定 4096 点）+ 缓存 Hann 窗 + 复用暂存区 + 以 `(offset,len)` 取代逐像素 `slice()` | ✅ 已完成，见下 |
| ④ **同步跟踪替代暴力对齐** | 用 1200 Hz 匹配相关取代"窗口主频 >1350 Hz 即跳出"的启发式 | ✅ 已完成：对齐抖动从数十采样点降到 **0.25 / 0.21 像素** |
| ⑤ **抗干扰解调** | 匹配滤波 + 时频域干扰抑制（窄带陷波、脉冲消隐）+ 软判决 LLR 直接喂 LDPC | ⏳ 阶段二正题；③④ 已把接口和平台准备好 |
| ⑥ **回归护栏** | golden 文件 + PSNR/时序断言，防止后续改动劣化 | ✅ 已完成（`tests/`，见第 6 节） |

### 5.1 ③ 的实测收益（同样是 AC5 的关键）

上游把 **51 个样本**（Martin M1 的像素窗，<1 个 1500 Hz 周期）塞进 **4096 点 FFT**，
且每次调用都 `new hann()` 分配窗口、`input.fill(0)` 清零 16 KB、调用方再 `slice()` 一次。
插桩归因：**99.9% 的解码时间花在这个逐像素估计上**（245,760 次调用）。

| 配置 | 单次估计 | 推算 245,760 像素 |
|---|---|---|
| 上游 4096 点 + 每次重分配 | 0.0787 ms | 19.3 s（in-situ 实测 0.42 ms，即 103 s——固定开销与 GC 主导） |
| 4096 点 + 缓存窗口 | 0.0763 ms | 18.7 s |
| **512 点 + 缓存窗口** | **0.00911 ms** | **2.2 s**（8.6×） |
| Goertzel 64 bin + 缓存窗口 | 0.01205 ms | 3.0 s（6.5×，因 FFT 更快而落选） |

**端到端实测**（同一份 115 秒 Martin M1）：**112.4 s → 4.17~6.04 s（约 20 倍）**，
PSNR 反而**高于**上游（28.10 dB vs 26.36 dB）——因为额外修正了同步对齐与窗口居中的缺陷。

### 5.2 精度/速度权衡的三档（已做成 UI 选项）

| 模式 | 快速 ×8 | 标准 ×16 | 精细 ×32 |
|---|---|---|---|
| Martin M1 | 4.2–5.6 s / 26.45 dB | 6.0–7.9 s / **28.10 dB** | 11.9–15.3 s / 28.06 dB |
| Scottie S1 | 5.8–7.6 s / 26.95 dB | 7.7–9.9 s / **28.83 dB** | 13.5–17.3 s / 28.78 dB |

（时间为多次运行的范围，差异来自机器负载；**PSNR 是确定性的，跨次运行完全一致**。
编码耗时：M1 0.66 s、S1 0.27 s、PD 120 0.37 s。）

**如实说明**：精细档（×32）**并不提升保真度**，甚至略低。原因是像素窗只有 51 个样本，
频率分辨率受"观测时长"这一物理上限约束；补零只能细化峰值定位，不能增加信息。
所以默认标准档（×16）是实测甜点，精细档仅保留供对比。

### 5.3 若要从头替换整个解调器

顺序建议：先用本项目已有的 `tests/verify-signal.js`（编码端、解码器无关的绝对真值）
和 `tests/diagnose-align.js`（同步对齐精度对照真值）把**地面真值**钉死，

## 7. 遗留限制与**不承诺**事项（如实说明）

1. **PD 120 只支持编码，不支持解码**（已与您确认的本阶段范围）。检测到 VIS 95 时返回结构化错误，
   而不是输出乱码。若阶段二要补，参数可直接从编码器反推，保证自洽。
2. **不是"秒级"解码**。`file://` 下 Worker 被浏览器拒绝（不透明源），无法把计算挪出主线程。
   实测 M1/S1 单张 4~8 秒（另有机器负载导致的波动，浏览器内见过 4.77~10.39 s）。
   若要秒级：需走"非纯前端模式"（本地服务 + Worker/WASM）——这正是 `Backend` 切换点存在的意义。
3. **精细档（×32）不提升保真度**（见 5.2），保留仅供对比。默认标准档。
4. **阶段一未实现任何隐写嵌入**。`identity` 嵌入器容量为 0；界面展示的容量是**解析估算**，
   不是已实现的信道容量。抗干扰能力（BER vs SNR）**本阶段未测**，因为还没有可测的载荷。
5. **未验证声学环路**（扬声器 → 麦克风）。只验证了数字域。真实回环会引入噪声与频偏，
   属阶段二抗干扰范畴。`Channel.freqOffset/awgn` 已就绪可用于量化。
6. **PD 120 的 Y 映射与上游 Web-SSTV 不同**（其 Y 带 +6 偏移导致白色只到约 2206 Hz）。
   本项目改用标准 BT.601 映射以恢复对比度；编解码自洽，但若与 MMSSTV 等做互操作对比需注意。
7. 上游 `sstv@1.0.0` **无测试、无 CI**，我不盲信其正确性：所有移植结果都与 PSNR 基线对照，
   并已修正其 3 处缺陷（见 1.4）。

## 8. 复现方式

```bash
cd robust-sstv
node tests/verify-signal.js     # 编码器独立验证（解码器无关）
node tests/roundtrip.js         # 端到端往返 + 上游交叉验证
node tests/perf.js              # 三档精度的时间/保真度权衡
node tests/diagnose-align.js    # 同步对齐精度（对照编码端真值）
node tests/browser-e2e.js       # 浏览器 file:// 真实 UI 端到端（AC1–AC4）
# 直接用浏览器打开 index.html 亦可手动验证
```

`tests/roundtrip.js` 与 `tests/browser-e2e.js` 需要 `.research/` 中的上游实现与 `pngjs`
（用于交叉验证与图像比对），缺失时自动跳过相应检查而不伪装通过。
