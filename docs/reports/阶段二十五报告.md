## 3. 判定结果与依据（报告第 3 项）

### **判定：情况 D** —— 真值脉冲流在该录音上不相干；同步检测无法建立稳定栅格

**依据（互相独立的三条）**：

| # | 证据 | 数据 |
|---|---|---|
| 1 | **栅格 inlier 率** | phigros **61%**（分段 50%/73%/78%）vs 对照组 **99.6%** ✗ |
| 2 | **Δ 散度** | 相对前一个真值的 Δ：MAD **5964 采样（287 像素）**、极值跨 **12 行** ✗ 对照组的对应量只有 **12 采样（0.58 像素）** ✓ |
| 3 | **无一致性候选** | Δ 既不 ≈ 0、也不 ≈ 7139、也不 ≈ 2·porch（最近的候选误差也有 234 采样）✗ |

**并且这不是"我们的公式错"，而是该录音自身的时钟特性**：

> phigros 的同步间隔**相邻差**很规整（中位 428.000、MAD 1 ms），
> 但**累积相位会漂移** —— 一条相位相干的栅格只能覆盖 50–78% 的脉冲 ✗
> 而**局部规整 + 长期漂移**正是"时钟不稳定"的特征（手机录屏丢帧/重复帧，或采样时钟游走）✓

**因此我没有修改回绕公式**（按你确认的规则："只有情况 B 才改"）✓
而且**不应该改**：回绕量与 `chanOffsets` 已被阶段二十三证明在我们自己的音频上**正确**
（三通道读到正确的槽、位移 ≤ 1 像素、S1 自往返 30.50 dB）；在一条时钟不稳的录音上
去改一个已被证明正确的公式，只会同时破坏自往返而对 phigros 无益 ✗

## 6. 对回绕公式的最终解释（报告第 6 项）

虽然本轮判定为情况 D、**不改代码**，你要求的"标准应该是什么"仍须给出：

### 6.1 Scottie S1 的行内几何（以 slowrx 为准）

```
[sep][G][sep][B][SYNC][porch][R]      ← 同步在行中；G、B 在同步之前
```

以**同步位置 T** 为原点（单位：ms；S1 的 `sep`=1.5、`chan`=138.24、`sync`=9、`porch`=1.5）：

| 位置 | 相对 T | 采样（48 kHz） |
|---|---|---|
| 行首（`sep` 之前） | **T − 279.48** | −13415 |
| G 起点 | T − 278.0 | −13344 |
| B 起点 | T − 139.74 | −6708 |
| **同步起点 T** | 0 | 0 |
| R 起点 | **T + 10.5** | **+504** |
| **下一行行首** | **T + 148.74** | **+7139** |

### 6.2 我们的实现

```js
chanTime = sepPulse + scanTime            // 139.74 ms
base     = syncPulse + syncPorch          // 10.5 ms
scottie: chanOffsets = [base + chanTime, base + 2*chanTime, base]   // R 紧贴同步，G/B 在其后
回绕（L868）: seqStart -= (chanOffsets[chanSync] + scanTime)
             = base + chanTime = 148.74 ms = 7139 采样
```

**注意**：7139 采样 **恰好等于"从同步到下一行行首"的距离** ✓ 所以这个回绕量**不是笔误**，
它与 Scottie 布局自洽；而 `seqStart` 在回绕前的参照系（`imageStart` 或 `alignSync` 的返回）
决定了它的实际效果 ✓ **阶段二十三的黑盒探针已经实测证明：净效果在我们自己的音频上是正确的** ✓

### 6.3 所以"标准应该是什么"

**结论：我们不需要"改成"任何值。** 理由：
1. 回绕量与 `chanOffsets` 构成**自洽的一对**，且**实测正确**（阶段二十三）
2. slowrx 的 Scottie 校正 `s − chan_len/2 + 2·porch` 是为它**自己的 `find_sync` 参照系**服务的，
   与我们的参照系不同；**照搬它才是引入错误** ✗
3. 本轮的差异来自**录音的时钟不相干**（§3），属输入特性，不是公式问题

**若要继续追 phigros**，正确的方向是**时钟/相位**而非行首公式：
- 用**短时**估计逐段跟踪该录音的**瞬时行周期**，看它是否在 428.22 ms 附近缓慢游走
- 若是，则解码器需要**更宽的逐行搜索窗**或**相位跟踪**（而不是改回绕）
- 这也与阶段二十二"带限无效"、阶段二十一"`clockScale` 假设被否决"的结论**一致**：
  三处独立线索都指向**逐行时序在真实录音上不稳**，而不是某个固定公式错 ✗
