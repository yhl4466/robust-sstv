## 2. 根因位置与修复方式（报告第 2 项）

### 2.1 根因

```js
const w = 2*Math.PI*CENTER/sr, c = Math.cos(w), s = Math.sin(w);   // ✗
let ci = 1, si = 0;
for (...) {
  const nc = ci*c - si*s, ns = si*c + ci*s; ci = nc; si = ns;     // 从 (1,0) 起【正向】旋转
  ...
}
```

递推式从 `(1,0)` 出发、形式为 `z ← z·(c + j·s)`，即 **`e^{+jw₀n}`（上变频）** ✗
而相位差分鉴频器假定基带已被**下变频** ✓ 于是报告值变成 `1900 − (f−1900)` = 镜像 ✓

**我上一轮纸上推演时按 `e^{−jw₀n}` 假设去算，得出"应该是对的"，正是这个假设与代码不符** ✗
—— 这是本系列第 N 次"纸面推演替代实测"的失败，**而这次是用最便宜的纯音测试一击定案的** ✓

### 2.2 修复

```js
const w = 2*Math.PI*CENTER/sr, c = Math.cos(w), s = -Math.sin(w);  // ✓ 真正的下变频
```

**改动位置（两处，同一行）**：
- `tests/diagnose-s1-quality.js` 的 `frequencyTrack()`
- `tests/diagnose-track-calibration.js` 的 `frequencyTrack()`（副本，必须同步修，否则参考测试自己还在报镜像 ✗）

**未改动 `js/` 下任何生产代码** ✓

### 2.3 为什么能确定它不在生产解码器里

| 证据 | 说明 |
|---|---|
| 生产用 `Estimator.peak` | 对 **FFT 幅度谱**做峰搜索 + 重心细化 → **对 I/Q 符号约定免疫** ✗不可能镜像 |
| 真实照片往返 **30.50 dB** | 镜像的频率轴会把灰度斜坡反向，PSNR 不可能达到 30 dB |
| 阶段二十三探针斜坡相关 **0.996** | 同上 ✓ |
| 阶段二十九真实录音 **0.5703** | 若频率轴镜像，行间相关不会随裁决层修复而上升 ✓ |

→ **生产链路健康，本轮修复的对象是"诊断用的尺子"** ✓

### 3.1 ★ 色边 45.35 的性质：**噪声，不是偏差**

**决定性证据**：三个通道在**同一灰度斜坡**上给出 **1894.5 / 1892.5 / 1893.3 Hz** ——
**最大差异仅 2 Hz** ✓ 若三通道之间存在系统性采样/标度差异，这个数字不可能这么小 ✓
→ 色边来自**逐像素随机误差**（同一像素在三个通道各测一次，误差独立）✗✓

**同一结论也解释了残余的 35.5 Hz 平均误差**：它是 `E|噪声|`，不是偏置 ✓
（修复镜像后误差**极值收窄到 ±260 Hz**，且**均值 35.5 远小于 MAD 79.9** → 典型的零均值噪声分布 ✓）

### 3.2 为什么噪声这么大（我的跟踪器 vs 生产估计器）

| | 我的诊断跟踪器 | 生产 `Estimator.peak` |
|---|---|---|
| 方法 | 1 ms 盒式低通 + **单样本相位差分** | FFT 窗（Hann + `windowFactor`）× 幅度峰 + **重心插值** |
| 等效平均 | ~48 样本 | 窗长 ~1 ms × 多 bin 插值 |
| 偏差 | 已修 | 无 |
| 噪声 | **大**（本轮实测 MAD ~80 Hz）| 小（照片往返 30.50 dB） |

→ **AC2/AC3 未达标的唯一原因是我的跟踪器噪声** ✗ **不是频率轴问题** ✓

## 4. order bug 的修复结果（报告第 4 项）

**修法**：不再用角色键回填，而是**直接按 `order` 映射物理槽 → 颜色角色**：

```js
const p0 = toGrey(planes[order[0]][y][x], lo, hi);   // order[0] 供红
const p1 = toGrey(planes[order[1]][y][x], lo, hi);   // order[1] 供绿
const p2 = toGrey(planes[order[2]][y][x], lo, hi);   // order[2] 供蓝
let R = p0, G = p1, B = p2;
```

**修复后（RGB 合成）**：

| 顺序 | 行间相关 | 与基线之差 |
|---|---|---|
| **RGB** | **0.3694** | 基线 |
| RBG | 0.3440 | −0.025 |
| **BGR** | **0.3694** | **0.000** |
| GRB | 0.3183 | −0.051 |

**四图现在互不相同** ✓ **AC4 达成** ✓

**两点解读**：
1. **RGB 与 BGR 相同（0.3694）是正确结果**，不是 bug：`rowCorr` 只测**绿色通道**，
   交换 R↔B 不改变绿 ✓ 反过来，**RBG 与 GRB 更差**，因为它们在绿通道上放了 B 或 R ✓
2. **所以"通道顺序"在相关意义上只区分"绿通道放谁"** → **RGB/BGR（绿=G）优于 RBG/GRB** ✓
   与 Scottie 标准一致 ✓ **但四种的差距（0.318–0.369）都在噪声量级** → **仍不能据此断定顺序错了** ✓

**色彩空间（重测，未受 order bug 影响）**：RGB **0.3694** vs YUV601 **0.2819** ✓ **RGB 明显更优** ✓
且 YUV 的**白占比 69.2% vs 41.0%** —— YUV 矩阵把色差当亮度用，导致大面积饱和 ✗ 进一步支持"Scottie 本就是 RGB" ✓
